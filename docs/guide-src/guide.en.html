1. What LegatorOCR is

LegatorOCR turns scans or photos of pages into a clean PDF with searchable text. It solves the same problem as ScanTailor (splitting pages, deskewing, cropping, cleaning), but adds PDF export and OCR. It is written in Rust, with its own code, each stage being a textbook technique. It runs locally, with no account and without sending the pages over the internet. Licence: MIT.

There are two ways of working, with the same engines underneath:

  • The graphical interface (legatorocr-gui): you add pages, see the original and the result side by side, correct page by page and export.

  • The command line (legatorocr): for large batches, for automation and for options the interface does not show.

What it does

  • splits double-page sheets into two pages, straightens skewed pages and crops the margins;

  • cleans the background, stains, punch holes, fingers on the edge and form lines;

  • writes PDF (including PDF/A for archiving) or images, with OCR in Romanian and 7 other languages;

  • also produces plain text (.txt) and hOCR, and can sign or date-stamp the PDF.

What it does not do (or has not been proven to do)

  • It is a trial version ({{VERSION}}). It has been run by the author and his assistant only on Linux; Windows, macOS and arm64 processors have not been tried by people.

  • OCR accuracy was measured on 8 good pages from a single Romanian magazine, against a reference text produced by another program, not corrected by a person. Do not take it as a guarantee for other kinds of print.

  • OCR can make mistakes: spot-check the important pages.

OCR

The program has its own OCR engine, which works without installation. Optionally you can install Tesseract, a separate program, which LegatorOCR uses automatically when it is present and has the requested language:

  • Linux (Debian/Ubuntu): sudo apt install tesseract-ocr tesseract-ocr-ron

  • macOS: brew install tesseract tesseract-lang

  • Windows: winget install UB-Mannheim.TesseractOCR and adding it to PATH

The Romanian model in the apt and brew packages is the small ("fast") variant. The "best" variant is downloaded manually and pointed to with --tessdata DIR. Which of them reads your pages better has not been measured.

Check the installation

Run legatorocr --doctor. It prints the version, the native OCR engine, Tesseract and the language models, then auxiliary tools (pdftoppm, gs, qpdf, mutool). A "missing" result for an optional tool is not an error; the message below it says whether it is needed. If something does not work, copy the whole output of the command into a report (see section 10).

3. The workflow, step by step

For each page, the program goes through the stages below in this order. The analysis is done on a copy of about 150 dpi, and the result is then applied to the scan at its full resolution.

  1. Orientation. Pages lying on their side (a quarter turn) are detected from the letters of the page: a page with pictures or with few words is not rotated by this test. For the exact direction, Tesseract (OSD) or manual rotation can be used.

  2. Sheet splitting. A landscape sheet with two pages is cut in the middle, at the empty band in the centre. It can be automatic, at the middle, or off.

  3. Deskewing. The skew angle is estimated from the text lines and the page is rotated back. The angle can be fixed manually.

  4. Content box. The area with text and images is found; scanner shadows and dust are ignored. Everything outside it is repainted in the paper colour.

  5. Margins and size. Margins in millimetres, optionally a fixed page size or the same size for the whole book.

  6. Straightening curved lines (optional). For dense book pages with lines curved near the spine.

  7. Lighting (optional). Evens out an uneven background.

  8. Cleaning and binarization. Removes stains, punch holes, fingers, lines; then black and white, grey, colour, mixed or hybrid.

  9. PDF and OCR. The PDF (or the images) is written and, if ticked, the text layer.

Automatic deskewing: a scan skewed by 3.5° (a test sheet generated by me) and the result; the program measured -3.50°.

Working rules that save time

  • First set the correct resolution (usually 300 dpi for text). The program reads it from the image if it is between 150 and 1200; otherwise it assumes 300.

  • Choose a profile suited to the material (section 6) before touching individual settings.

  • Process 10–20 pages as a trial, check the result, then start the large batch.

  • The interface marks pages "to check" (blank page, borderline skew, nothing found, content stuck to the edge). Go through them with the "Next" button.

Bent pages, a slanted cut and settings per page

Three things for sheets photographed by hand:

  • Slanted cut line. With "Draw erase zones on the original" ticked and the Cut line type, a "Line lean" slider (−20° to 20°) tilts the line; each page keeps its side of the slanted line and the other side is painted with the paper colour. Right-click the line to remove it and reset the lean. On the command line: --cut-angle DEGREES.
  • Keystone correction. Two sliders in the "This page" bar ("Keystone top–bottom", "Keystone left–right", ±30 %) straighten a sheet photographed at an angle before the cut. The Auto keystone button (after the pages are split) measures each page — the tilt of the text lines and the width of the text at top and bottom — and keeps a correction for that page only. It is careful on purpose: when there are too few lines or the measurements contradict each other it leaves the page as it is. Check the result, with Undo at hand. The −45°/+45° buttons stay. On the command line: --keystone-v and --keystone-h (percent).
  • Settings per page. "Settings for: All pages / This page only", above Output and Clean-up, applies the output mode, threshold, despeckle and the other clean-up settings to a single page of a cut sheet; the green content box changes only the page it is dragged on. In a project: page1.KEY = VALUE / page2.KEY = VALUE under [sheet]. A click on a processed page selects it (blue frame): the output mode (gray, black-and-white, mixed), clean-up, keystone, the green box and the OCR pencils then work on that page alone. OCR zones you draw stay with that page (page1.page_ocr_zones, page_ocr_ignore).

The bar below the preview holds the content box, the OCR pencils and Auto OCR pencil (separately for the left and the right page): it puts the OCR zone on the content of that page.

The manual tilt works on the selected page (left or right) of a cut sheet: each page can have its own angle (page1.page_skew, page2.page_skew).

All options and the user guide

The All options… button in the top bar opens a window with all the command-line options (over 200), grouped by topic: pages and order; straightening, cropping and cleaning; outputs (PDF, images, documents); OCR and text; archiving, signing and verification; search and comparison; batches, system and modules. The list is read from the command-line program shipped with the window itself, so it always matches the edition you have.

The "All options" window, with the "Pages and order" group open, --duplex-adf and --dry-run ticked and the result of the run: the order in which the six pages of the stack would be processed (test pages made by me).

  • Search by name (pdf, dry) or by a word from the description; the groups with results open by themselves. "Only the chosen ones" shows what you have ticked or filled in.

  • Empty boxes are not sent: an option with a value enters the command only when you type something (or choose from a list). The Choose… button opens the file or folder dialog. For options that can be repeated (for example --erase) you write one value per line.

  • Use the pages and settings from the window (ticked by default): the command receives the loaded pages, with the adjustments of each, through a temporary project. The processing settings of the main window (straightening, cropping, cleaning) take priority; here you fill in the outputs and the special functions. Untick it for commands without pages (--doctor, --verify-sums) or write the input files in "Other arguments".

  • The equivalent command is updated as you choose; you can copy it and use it in a terminal or in scripts. Run executes it and shows the output below; Stop interrupts it. Relative paths are relative to your home folder.

  • The option descriptions are in English, as on the command line; the rest of the window is in the chosen language.

The Help menu has the link to this guide: User guide (online, always up to date) opens the latest version published on legatorocr.chiuta.ro, and Guide of this edition (it appears when the PDF file is next to the program, as in the published archives) opens the copy shipped with the program. The guide is rebuilt for each edition, and the publication of an edition is stopped if the guide does not mention its version.

Checked: the window, the search, the ticking, the running of a command with the pages from the window (the screenshot above) and the opening of the Help menu, on Linux, on a virtual screen. Not checked: Windows, macOS and arm64; the actual opening of the guide in a browser (I only checked the menu); the "Choose…" dialogs; the translations of the window's new texts (written automatically).

Collections

A collection gathers newspapers, magazines, books and the like in one .lgrcol file (JSON). Keep it in the folder with the scans: paths inside the file are written relative to it when the target lies under a folder they share, so the folder can be moved or copied. Each item has a kind, title, issue or volume, date or year, languages, sources (images, a folder of images, a PDF, a saved .lgr project), the PDF made from it, a profile, a status (to do, processed, OCR done, checked), page count, tags and notes.

legatorocr collection new Archive/ --name "Old papers"
legatorocr collection add Archive/old_papers.lgrcol --folder Archive/scans
legatorocr collection list Archive/old_papers.lgrcol
legatorocr collection run Archive/old_papers.lgrcol --out Archive/pdf
legatorocr collection search Archive/old_papers.lgrcol "Scînteia"

  • add --folder: each PDF, .lgr project and subfolder of images becomes an item. Title, kind, date and issue are guessed from the name: scinteia_tineretului_1977_09_8801.pdf gives a newspaper, "Scinteia Tineretului", 1977-09, no. 8801. It is only a guess (file names carry no diacritics; the kind rests on a few key words and on the numbering: a full date or an issue number of 500 or more is taken for a newspaper); correct it in the window.

  • run processes the items whose status is "to do", each with its own profile (else the collection's, else the engine defaults), through the same code as the command line and the window (run_export). An item that fails (missing source, unknown profile, unreadable page) is marked with the reason and the others go on; the collection file and the index are saved after every item, so a cancel or a crash loses nothing that was done. PDFs go next to the collection file, or to --out. With OCR (on by default; --no-ocr turns it off) the recognised text of every page goes to NAME.lgrindex; the OCR language comes from the item's languages, else the profile's ocr_langs, else Romanian. An item that failed is not tried again unless --retry-failed or --item ID is given.

  • search looks in that index. Case, diacritics and the old Romanian spelling do not matter (Scînteia finds Scânteia, sînt finds sunt). It prints item, page and a snippet: pages with the words next to each other first, then (marked) pages that have all the words apart.

  • The Collections… window (File menu, or Ctrl+K): a table with kind letter, title, issue/date, pages and a status chip (colour and text), with filter and sort; the details on the right; Add files, Add folder, Process selected, Process all pending (with progress and Cancel), Open PDF, Show folder; a search box over the whole collection with clickable results. Its texts exist in the 8 languages of the window.

Tested: unit tests (name guess, relative paths, damaged files, search with diacritics, a batch that goes on after a failure and after a panic, cancel), a test of the real binary, and one run with real Tesseract on two synthetic pages, also after moving the folder.

Limits: the window was written and compiled but nobody has looked at it on a screen or clicked through it (only its filter, sort and texts are unit-tested); only text recognised by collection run is searchable (a PDF that already has a text layer is not indexed); the whole index is read into memory (collections of tens of thousands of pages were not measured); a search hit names the page, but the PDF viewer opens at page 1; two programs writing the same file at once: the last one wins; the window runs Tesseract from the PATH, not the path set in the main window; the old-spelling rule is the one of --ocr-modern-spelling and can join different words (mână / mină).

5. The command line: recipes for frequent tasks

General syntax: legatorocr INPUTS... [options]. The inputs can be images (PNG, JPEG, TIFF, BMP), scanned PDFs or a folder. legatorocr --help lists all the options; --list-profiles shows the profiles. The options in the recipes are checked automatically before each edition, so they really exist; the recipes themselves have not all been tried on real material.

Scanned book → PDF with searchable text

legatorocr scans/*.png --profile book-bw --ocr --lang ron --pdf carte.pdf --pdfa --txt carte.txt -o pages

--pdfa writes PDF/A-2b for archiving, and --txt also saves the text. -o pages is the folder for the processed images.

The recipe on 4 test files: 6 pages in carte.pdf. With --pdfa the program writes PDF/A-2b.

Phone photos → clean pages

legatorocr photos/*.jpg --profile phone-photos --pdf pagini.pdf -o pages

The profile evens out the lighting, corrects perspective, wipes the background around the page (--trim-background), cuts open books in the middle, widens the skew range and removes fingers without touching the text. A page that comes out without text is read a second time on its content only. For uniform A4 pages, with enlarged text, use --profile phone-photos-a4. Several photos of the same page can first be combined with --fuse-frames (it helps with strong noise; with moderate noise it does not). The option takes an output file: legatorocr photo1.jpg photo2.jpg photo3.jpg --fuse-frames page.png, then you process page.png as usual; the first photo is the reference.

--fuse-frames with three photos of the same page: it aligns them and writes fused.png from 3 of 3 frames.

Archive copy with proof of integrity

legatorocr scans/*.png --profile registre-manuscrise --ocr --lang ron --pdf registru.pdf --pdfa --checksums --archive-package registru-arhiva -o pages
legatorocr --verify-sums registru-arhiva/SHA256SUMS.txt

The package keeps the originals, the project, the OCR words with confidence, the outputs and a RUN.txt that says how to resume the work. For copies on other disks: --backup-from and --backup-to.

The archive package created and verified: "5 ok, 0 mismatched, 0 missing".

Hiding names and numbers before sharing

legatorocr scan.png --ocr --lang ron --redact email,phone-ro --format none --pdf redactat.pdf

The words found are blacked out in the image and removed from the text. Check the result with your own eyes: a word that OCR did not recognise is not hidden.

Real result: the phone number was hidden, but the e-mail address was NOT, because OCR read "@" as "G" (ion.popescuGexample.com) and the e-mail pattern did not match. This is why you must check the result with your own eyes. Since pre.20 the program writes at the end how many words each pattern covered and warns when a pattern found nothing or when words that look like addresses or long numbers remain in the text, exactly as in the screenshot above.

A large batch on several computers

legatorocr scans/*.png --shard 1/3 --profile book-bw --pdf part1.pdf -o pages1
legatorocr --merge-pdf part1.pdf part2.pdf part3.pdf --pdf carte.pdf

Run the same list on each machine, with a different --shard. For low memory: --max-memory 500. For unknown or hostile files: --isolate-decoders.

The batch split in two (--shard 1/2 and 2/2) and then joined with --merge-pdf.

Signing a PDF

LEGATOROCR_P12_PASS=... legatorocr --sign-pdf registru.pdf --sign-p12 certificat.p12 --sign-name "Name"
legatorocr --verify-pdf-signatures registru.signed.pdf --sign-ca ca.pem

The legal level of the signature is that of your certificate. The certificate password is given through the environment variable, not on the command line. The time stamp (--sign-timestamp) was checked only with a local authority over HTTP, not with a real one over HTTPS.

Signing and verification with a test certificate created by me (not a real certificate). "time stamp inside: none": I did not request a time stamp.

A stack scanned on a feeder, page order and range

Many scanners with a feeder pass the stack once for each side: first all the fronts (1, 3, 5…), then all the backs, in reverse order (6, 4, 2). The files come out in scanning order, not in the order of the book. --duplex-adf puts them in reading order: front 1, back 1, front 2, back 2… The number of pages must be even (otherwise the program stops with a message).

Six files in scanning order (scan_001 … scan_006). --dry-run shows the order in which they would be processed and which files would be written, then stops without processing anything: scan_006 ends up in position 2, scan_005 in position 4.

The same command without --dry-run, with native OCR: the text comes out in the order "Pagina 1 … Pagina 6" (test pages made by me, not a real book).

Other ordering and selection options (they can be combined; the range applies to the numbering of the input files, starting from 1):

  • --pages 1-10,15,20-: keeps only the pages indicated; 20- means "from 20 to the end". It also works on pages taken from PDFs or from multi-page TIFF sheets.

  • --reverse: reverses the order (a stack scanned from the last page).

  • --dry-run: checks a large batch before the long run.

Checked: the order and the range with automated tests and with six test pages; I did not try a real scanner with a feeder. The options can also be chosen from the window, under "All options…" (section 4).

Clean text: your own corrections, running heads and cedilla

For the .txt and .docx files (the text layer in the PDF, hOCR and JSON keep the words as read, unchanged):

  • --clean-text: ș and ț with a comma below, words broken at the end of a line joined (with the hyphen kept when the two halves are words from the list and simple joining is not), typographic quotation marks, spaces next to punctuation. --cedilla writes ş and ţ instead, for programs and fonts that do not know the comma letters.

  • --find-replace FILE: your own corrections, one per line, wrong => right. Lines that start with # are comments. Only whole words match (Ion => Ioan does not touch "Ionescu") and they are applied in the order of the file, after --clean-text. Useful for proper names, abbreviations or a stamp that the engine always misreads in the same way.

  • --drop-running-heads: leaves out the printed running heads, footers and page numbers: the first or last line of a page that repeats (digits do not count) on at least half of the pages; at least four pages are needed. The lines removed are listed on stderr, so that you can see what went.

The rules file (first block) and the same two lines read from the test page without and with --find-replace: "Ionescu" became "Ionescu-Vale" and "ha" became "hectare".

On six test pages with the running head "Anuarul Văii Mari" and a number, the program removed six running-head lines; the text starts directly with "Pagina 1". Note: the rule removes any first/last line that repeats, so in a book where the last line of each page is similar (for example "Shelf position: 14") those lines would go too; this is why they are listed. The function was checked with tests and on a few pages, not on a large set of books.

The formats of the text fields

These fields exist in the settings, but it is easier to draw on the original (section 4):

  • Erase zones and Picture zones: x,y,w,h in millimetres from the top-left corner of the page. Several zones are separated with semicolons: 10,20,30,40;50,60,20,20. At most 64; width and height must be positive. If the form is wrong, the field turns red.

  • Straightening guide lines: x,y x,y x,y;x,y x,y x,y, with fractions between 0 and 1 of the page already straightened (0,0 = top-left corner). Each line has at least two points; at most 64 lines in total.

  • On the command line: --erase X,Y,W,H (repeatable) and --dewarp-guide "X,Y X,Y …" (repeatable).

7. OCR: engines, languages and accuracy

The "Searchable text (OCR) in PDF" tick box (or --ocr on the command line) adds an invisible text layer over the image. The language is chosen from "Recognised languages" (or --lang ron); it can be combined, for example ron+eng. The languages of the interface and of the built-in engine: Romanian, English, French, Italian, Spanish, Portuguese, German, Hungarian.

The OCR section of the settings: the "Searchable text (OCR) in PDF" tick box, the recognised languages (those installed in Tesseract) and the segmentation mode. In the screenshot Tesseract 5.3.4 was installed, which is why all its languages appear; I used the ron choice in the next figure.

With OCR ticked, "Also save .txt text" and "Also save hOCR" appear. Here the chosen language is ron.

After the export, the bottom bar shows: "PDF saved: … — 3 pages, 36 words recognised". (I started the export with a test mechanism of the program, not from the file dialog.)

Three engines

EngineHow you choose itNotes
Native (the program's own)--engine nativeno installation, written in Rust; model trained on synthetic text, then adjusted on lines from a Romanian magazine and from a 1960 textbook

The same test page read by the two engines. Both made the same mistake: "@" came out as "(a" with the native engine and as "G" with Tesseract.

The measured figures (and what they do not say)

8 good pages from a Romanian magazine were measured, against a reference text produced by ABBYY, not corrected by a person. The character error rate, with diacritics (the original measurement, from edition 0.2.0-pre.21; on a new measurement in pre.26 on the same 8 pages, with the same method, the native engine gave 2.76 %; I have not investigated the difference from 2.55 %):

EngineCharacter errors
Native2.55 %
Tesseract (ron)4.32 %
OCRmyPDF (with Tesseract)4.62 %

Read simply: the native engine makes fewer mistakes on this type of print. But it was tuned on text from the same sources, so it cannot be said to be better in general. On other documents, especially old or unusual print, it may be weaker than Tesseract. Recognition of whole words is almost equal between the engines (about 92 %).

Accurate mode and old orthography

  • --accurate (native engine): each line is read three times (shifted by one pixel up and down) and the probabilities are averaged. It is slower (measured: 18 % to 74 % more time) and helped only on the magazine pages (character error 3.66 % → 3.39 % on 12 pages); on books and brochures it changed nothing measurable. It is off by default.

  • The Romanian word list also accepts the orthography of 1953–1993 (cuvînt, romîn, sînt): on five pages from a 1960 textbook, transcribed by hand, correct characters rose from 99.6 % to 99.7 % and words from 96.0 % to 96.3 %. A small difference, on five pages.

  • Words are split at wide spaces even when the network did not write a space: the cells of a table no longer come out stuck together (CantitatePreț). A table with lines is found as a single table (Excel: --tables-xlsx); a table without lines is still found as two tables (left and right), an unsolved problem.

Tips

  • On your own documents, compare the engines on 5–10 pages before the batch: scripts/compare-ocr-text.py measures the errors against reference texts that you have.

  • Pages under 250 dpi are automatically enlarged before recognition.

  • Pages with illustrations or diagrams can produce meaningless text in the area of the image (Tesseract read an illustration as text on one of the measured pages). Check these areas.

  • Any OCR can invent or lose words. For deeds, registers or figures, spot-check.

About PDF/A

The program writes PDF/A-2b with an embedded font and sRGB profile. Conformance was checked on samples, not with veraPDF on every output. If an institution requires certified conformance, run your own validator on the final files.

About ScanTailor projects

--project FILE.ScanTailor opens a ScanTailor project: the scan list and the rotation per image are taken over, while the skew, the splitting and the content box are found again. The reader was written from the description of the format and tested on a hand-made project, not on files from every ScanTailor version.

Known limits of edition {{VERSION}}

  • Auto keystone: checked on synthetic sheets and on 67 phone photos of a single book (133 pages), where it left most pages alone and lowered the measured tilt on the rest; nobody has judged the result by eye on other books, or on pages with large pictures, tables or very short lines, where it may do nothing or too little. The settings per page and the cut-line lean were tried on synthetic sheets and in tests; the table pencil makes the OCR read the zone as one block, it does not find cells.

  • Rotation by 90°: on a page with a photograph of ornaments (page 15 of a PDF) a tester on Windows saw the rotation jump from 90° to 180°. I reproduced part of the problem on Linux: in pre.18, with "Detect page lying on its side" ticked (the default), the program wrongly rotated this page by 90°, although the original is upright (the figure in section 4). The threshold in pre.19 was too fragile (I have meanwhile discovered that another page of the same PDF, page 13, was also rotated wrongly). In pre.20 the detector counts only pieces the size of a letter and abstains on pages with pictures or with few words. On 98 book pages (rotated at 0° and 90°) and 5 pages with pictures, the result is identical to pre.18, apart from page 13 (rotated wrongly in pre.18, now upright) and one page with a photo lying on its side, which the detector no longer turns (OSD and manual rotation remain). Checked on the command line, on Linux, on a small corpus. The probable cause of the jump (automatic orientation added on top of the manual rotation) was fixed in pre.18: after a click on rotate the page stays locked, and four clicks give 90°, 180°, 270° and back to 0° (checked in the window, on Linux). What exactly the tester saw on Windows 11 I could not check. If a page with pictures is still rotated wrongly, untick "Detect page lying on its side" or use --no-auto-orient.

  • The work area, the movable cut line, the erase and picture zones, the grid of points, Undo and Ctrl+Z, the content box, OCR and PDF export were tried in a real window on Linux, with a simulated mouse (the screenshots in the guide). Resizing a zone from a corner worked in the window. The native file dialogs ("Export PDF…", "Save project", "Open project") worked with the GTK dialog of an xdg portal on Linux; on Windows and macOS I did not try them. If the system has no dialog at all, since pre.21 the window says so instead of doing nothing (you can drag the files into the window or use the command line). Saving a custom profile worked. The effect of the cut line I checked through automated tests, with --cut-at and in the window (a double sheet cut into two unequal pages, 524 and 674 px). For sheets rotated by 90° or 270° (since pre.21) the pages come out one below the other; this is checked only through an automated test, not in the window.

10. How to report a problem

The most useful contribution is a report from a system the author has not tried. It takes five minutes:

  1. Download the latest edition for your system.

  2. Run legatorocr --doctor and copy the whole output.

  3. Run a page you can share: legatorocr PAGE.jpg --ocr --pdf result.pdf -o pages.

  4. Open result.pdf: is the page upright and cropped as it should be? Can the text be selected and searched?

Send, as an issue in the chiuta/LegatorOCR repository (or by e-mail):

  • the system and its version (for example Windows 11 23H2, macOS 15 arm64, Debian 12 arm64);

  • the LegatorOCR version;

  • the output of the --doctor command;

  • the command you ran (or the setting in the interface);

  • what you expected and what happened (error text or screenshot);

  • whether the image can be shared.

Do not send documents with personal data. An "everything worked" report is still useful: it is the only way the author learns that a system works.

Security problems are reported according to SECURITY.md, not publicly.
