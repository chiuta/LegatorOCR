Site de apresentação: <https://legatorocr.chiuta.ro> (código-fonte em `docs/`).

Pós-processador independente em Rust, para livros digitalizados:
**dividir → corrigir inclinação → recortar → margens → limpar / binarizar → PDF com camada de texto OCR pesquisável.**
Mesmo *fluxo de trabalho* das ferramentas clássicas de tratamento de digitalizações, código independente. Interface gráfica
(Windows, macOS, Linux) e linha de comandos.

## Início rápido

**GUI** — execute `legatorocr-gui` (ou abra `LegatorOCR.app` no macOS). Arraste as digitalizações ou uma pasta para a
janela (ou use *Add*), escolha as definições à direita, verifique a pré-visualização **Side by side / Original / Processed**,
ajuste páginas individuais (rodar, dividir página, inclinação manual) e depois **Export PDF…** ou
**Export images…**. As definições mantêm-se entre sessões; **File → Save project…** guarda a lista de páginas com
os ajustes de cada página (rotação, divisão, inclinação, correção da caixa de conteúdo) num ficheiro de texto simples `.lgr`.
Idiomas (seguem o idioma do sistema; mudam-se no menu): Română, English, Français, Italiano,
Español, Português, Deutsch, Magyar.

**Visita em vídeo à janela** — 11 clipes sem som (cerca de 14 minutos no total, legendas em oito idiomas) que percorrem cada função da interface gráfica: [docs/video/gui/](docs/video/gui/), ou a secção *Visita à janela* da [página do projeto](https://legatorocr.chiuta.ro/). Gravados em Linux com digitalizações de exemplo geradas e a interface em inglês; arrastar ficheiros para a janela é apenas descrito, não mostrado.

**CLI**

```
legatorocr scan_*.png --mode bw --dpi 300 --margin 6 --page-size a5 \
    --pdf carte.pdf --ocr --lang ron+eng
```

Modos de saída: `--mode color|gray|bw|mixed|hybrid`. **mixed** = texto nítido de 1 bit mais manchas de imagem
a cores encontradas automaticamente; **hybrid** = o mesmo sobre um fundo de papel de baixa resolução
(`--hybrid-dpi`), o que dá páginas de livro a cores de cerca de 60–100 KB em vez de 700 KB+.
Mais: `--threshold sauvola|wolf|niblack|nick|bradley|otsu`, `--normalize` (uniformizar a iluminação),
`--dewarp` (endireitar linhas curvas), `--dewarp-guide "X,Y X,Y …"` (indica a linha curva como pontos, frações 0–1 da página já sem inclinação; repetível; substitui a estimativa automática), `--output-dpi N`, `--uniform-size`, `--align top-left`,
`--project FILE.lgr` / `--save-project FILE.lgr`. Os TIFF de várias páginas são lidos página a página
(`scan.tif#3` endereça uma página).

`--skip-blank`, `--skew DEG` (correção fixa), `--rotate 90`, `--pdf-quality N` (0 = sem perdas),
`--format png|jpeg|tiff|none`, `--tessdata DIR`, `--psm N`, `--min-conf N`, `--keep-going` (ignora entradas
ilegíveis, estado de saída 2) — veja `legatorocr --help`. Pode indicar-se uma pasta em vez de ficheiros. A resolução é
lida do cabeçalho PNG/JPEG quando indica 150–1200 dpi (caso contrário 300; substitua com `--dpi`); a
rotação EXIF da câmara é aplicada e a transparência é achatada sobre branco. Números fora do intervalo são rejeitados
com uma mensagem clara, em vez de produzirem tamanhos de página absurdos.

## Opções menos comuns

`-o, --out-dir DIR` pasta para as imagens das páginas processadas · `--no-deskew`, `--max-skew DEG`, `--no-auto-orient`
(páginas deitadas), `--no-despeckle` (manter pontinhos) · `--sauvola-k K` (sensibilidade do preto e branco),
`--picture-sensitivity 0-1` (mixed/hybrid) · `--jpeg-quality N` (com `--format jpeg`) · metadados do PDF
`--subject`, `--keywords` · `--tesseract PATH` (motor externo) · `--burst-gap SECONDS` (com `--burst`),
`--fuse-max-shift PX` (com `--fuse-frames`) · `--watch-interval SECONDS`, `--watch-skip-existing` (com
`--watch`) · `--version`. `--project FILE.ScanTailor` abre um projeto ScanTailor: a lista de digitalizações e a rotação por imagem são aproveitadas; a inclinação, a divisão e as caixas de conteúdo são encontradas de novo (o leitor foi escrito a partir da descrição do formato e testado num projeto feito à mão, não em ficheiros de todas as versões do ScanTailor).
Pode ligar-se outro motor de OCR: `--engine tesseract --tesseract PROGRAM` aceita qualquer programa que fale a linha de comandos do Tesseract e devolva o seu TSV (modelo e contrato: `docs/examples/external-ocr-engine.py`; um modelo generativo pode aí inventar palavras, por isso mantenha uma pessoa no circuito). Velocidade e precisão do OCR nas suas próprias páginas: `scripts/bench-real.py DIR` (imagens com um `NAME.txt` de referência cada; `--partial` para referências que cobrem parte de uma página).
**Ponte ONNX OCR** (`scripts/engine-onnx.py`; Python com onnxruntime, numpy, Pillow): executa um par PaddleOCR PP-OCR (detetor de texto DB e depois um reconhecedor CTC) como esse motor externo, de modo que um modelo à sua escolha possa ser o motor de OCR sem que o LegatorOCR inclua quaisquer pesos. Descarrega os modelos você mesmo, por exemplo os modelos de deteção e reconhecimento PP-OCRv6 da lista de modelos do PaddleOCR convertidos para ONNX (`pip install paddle2onnx` e depois `paddle2onnx --model_dir DIR --model_filename inference.pdmodel --params_filename inference.pdiparams --save_file det.onnx --opset_version 14`; ou uma exportação ONNX pronta de um repositório de modelos), mais o dicionário de caracteres correspondente (estilo `ppocr_keys_v1.txt`: um caractere por linha; a ponte coloca o espaço em branco CTC na classe 0 e acrescenta a classe do espaço, como faz o PaddleOCR). Utilização: `export LEGATOROCR_ONNX_DET=det.onnx LEGATOROCR_ONNX_REC=rec.onnx LEGATOROCR_ONNX_DICT=dict.txt` e depois `legatorocr scan.png --pdf out.pdf --ocr --engine tesseract --tesseract scripts/engine-onnx.py`. Definições (variável ou a mesma opção, `--onnx-det/-rec/-dict/-size/-rec-height/-thresh/-unclip/-space`): lado do detetor 960, altura do reconhecedor 48 (32 para modelos mais antigos), limiar 0,3, unclip 1,5. As caixas são alinhadas com os eixos, sem texto rodado nem classificador de orientação; as palavras são separadas na classe do espaço usando o passo temporal CTC (caixas aproximadas); a confiança é a probabilidade de pico média x 100. **O que está verificado:** apenas a canalização, com pequenos modelos ONNX sintéticos (`scripts/test-engine-onnx.py`: ligações, coordenadas das caixas após o redimensionamento, descodificação CTC, TSV através da CLI). **Não verificado:** a precisão do reconhecimento com modelos PP-OCR reais (nenhum pôde ser descarregado onde isto foi escrito) e se os diacríticos romenos (ă â î ș ț) saem corretos: isso depende do modelo e do dicionário que escolher; verifique nas suas próprias páginas com `scripts/bench-real.py` antes de confiar nele. Como qualquer motor baseado em modelo, pode inventar texto.
**Família docTR da ponte ONNX (ROADMAP 4.33)**: o mesmo script lê modelos docTR/OnnxTR, incluindo o reconhecedor com cabeça romena de `tools/ocr-train/romanian_head.py` (ă ș ț Ă Ș Ț acrescentados a um CRNN docTR congelado). `scripts/get-romanian-doctr-models.sh [mobilenet|resnet] [DIR]` descarrega os modelos originais dos ficheiros da release do OnnxTR no GitHub, constrói o reconhecedor romeno (`romanian_head.py splice`, requer python3 com onnx) e imprime o comando exato. Utilização: `export LEGATOROCR_ONNX_FAMILY=doctr LEGATOROCR_ONNX_DET=DIR/db_mobilenet_v3_large-4987e7bd.onnx LEGATOROCR_ONNX_REC=DIR/crnn_mobilenet_v3_small_ro.onnx LEGATOROCR_ONNX_DICT=DIR/vocab_ro.txt` (ou `--onnx-family doctr` etc.), e depois `legatorocr scan.png --ocr --engine tesseract --tesseract scripts/engine-onnx.py`. O detetor encontra palavras (entrada 1024x1024, limiar do mapa de probabilidade 0,3), cada recorte de palavra é lido a 32x128 com descodificação CTC gananciosa (espaço em branco = última classe; `--onnx-dict` é o vocabulário como uma única cadeia), e o script agrupa as palavras em linhas e colunas por si próprio, de modo que o TSV fica na ordem de leitura. Medido através da CLI real em 12 páginas de uma revista romena (referências ABBYY, não verificadas à mão; 2 núcleos de CPU): db_mobilenet_v3_large + crnn_mobilenet_v3_small romeno, CER GOOD8 com diacríticos 4,26 %, recuperação exata de palavras 88,2 %, cerca de 3,4 s por página (a opção `resnet`: 3,67 %, 89,6 %, cerca de 18 s por página); Tesseract `ron` nas mesmas páginas 5,25 %, 91,3 %, 2,7 s por página. Outros tipos de letra e digitalizações: não medidos. Resultado medido numa linha: ao nível do Tesseract no erro de caracteres em páginas de texto simples (melhor apenas onde o Tesseract lê uma ilustração como texto), atrás na recuperação de palavras, uma revista, referências não verificadas à mão; ver ROADMAP 4.36.
São aceites os nomes do OCRmyPDF: `-l/--language`, `--force-ocr`, `--redo-ocr`, `--skip-text`, `--deskew` (sem efeito, ativo por
omissão), `--rotate-pages`, `--output-type pdf|pdfa|pdfa-1|2|3`, `-j/--jobs N`, `--sidecar FILE`, `--image-dpi`
(a saída é nomeada com `--pdf FILE`; não há saída posicional). `scripts/check-options.py` lista todas as opções que não têm documentação ou teste.

## Instalação

Descarregue o arquivo para a sua plataforma na página de Releases, ou compile a partir do código-fonte:

```
cargo build --release          # target/release/legatorocr and legatorocr-gui
scripts/package.sh <target>    # e.g. x86_64-unknown-linux-gnu → dist/LegatorOCR-<ver>-<target>.tar.gz
```

| Plataforma | Artefacto | Notas |
|---|---|---|
| Linux x86-64 / ARM64 | `.tar.gz` (+ `.desktop`) | requer OpenGL 2+ e X11 ou Wayland |
| Windows x86-64 | `.zip` | requer OpenGL 2+ (qualquer controlador de GPU; sessões RDP simples podem não o ter) |
| macOS Apple-silicon / Intel | `.zip` com `LegatorOCR.app` | **não assinado**: primeiro arranque com clique direito → Abrir, ou `xattr -dr com.apple.quarantine LegatorOCR.app` |

**O OCR funciona logo de origem** com o motor nativo incorporado (`legatorocr-nocr`, Rust puro, sem
instalação; `--engine native`). Lê os oito idiomas da interface com um só modelo mais listas de
palavras por idioma. O seu modelo foi treinado em texto sintético e depois afinado em linhas digitalizadas reais de uma revista romena e de um manual escolar de 1960 (as digitalizações não estão neste repositório; proveniência e questões de licença em aberto: `docs/audit/assets-licences.md`): em páginas sintéticas limpas e moderadamente degradadas comete menos de 1 % de erros de caracteres, mas digitalizações reais de impressão antiga ou invulgar podem ser piores do que o
Tesseract. Por isso, `--engine auto` (predefinição) usa o **Tesseract quando este está instalado com os
idiomas pedidos** e recorre ao motor nativo caso contrário; `--engine tesseract` força-o.
Tesseract (executado como programa separado; a aplicação encontra-o no `PATH`):
`sudo apt install tesseract-ocr tesseract-ocr-ron` · `brew install tesseract tesseract-lang` ·
Windows: `winget install UB-Mannheim.TesseractOCR` (adicione-o ao `PATH`).
Estes nomes de pacotes foram verificados em 2026-11-04 (`docs/audit/ocr-externals.md`): o Debian 13 e o Ubuntu 24.04 têm `tesseract-ocr` e `tesseract-ocr-ron`; o `tesseract` do Homebrew é o 5.5.4 apenas com `eng` e `osd`, e o `tesseract-lang` traz os modelos *fast*; o pacote winget está atrasado (5.4.0 de 2024-06). O ficheiro `ron` do `apt`/`brew` é o modelo pequeno *fast* (cerca de 2,4 MB, 2017); o modelo *best* (9,6 MB, do mesmo ano, mesmo histórico de repositório) é uma descarga manual de `ron.traineddata` de `tesseract-ocr/tessdata_best` para a pasta tessdata (`--tessdata DIR`). Qual dos dois lê melhor as suas páginas não foi medido aqui.
A aplicação procura também nas pastas de instalação habituais (Homebrew `/opt/homebrew/bin`, `/usr/local/bin`,
`C:\Program Files\Tesseract-OCR`), pelo que uma aplicação aberta com duplo clique funciona sem editar o `PATH`.
Sem o Tesseract usa-se o motor nativo (o interruptor de OCR continua ativo). Um comando para todos os auxiliares opcionais: `legatorocr --install-modules` (imprime os comandos) e `legatorocr --install-modules --yes` (executa-os).
Uma compilação **sem o modelo reconhecedor incorporado** (por exemplo enquanto a sua licença não estiver resolvida, `docs/audit/assets-licences.md`) é `cargo build --release --no-default-features --features lexicon` (acrescente apenas `--no-default-features` para deixar de fora também as listas de palavras); toda a bateria de testes passa assim, `--doctor` passa então a indicar o motor nativo como ausente, e o OCR precisa do Tesseract ou de um motor externo.
`--auto-rotate` / a caixa de seleção OSD precisam adicionalmente de `osd.traineddata` (parte dos pacotes padrão).

## Pipeline

| Etapa | Método (técnicas padrão, de manual) |
|---|---|
| Orientação | energia do perfil de linhas/colunas em torno da banda do passo de linha (0° vs um quarto de volta); Tesseract OSD opcional para a direção exata; ou `--rotate` |
| Divisão de página | goteira = banda de colunas mais vazia no centro de uma folha apaisada (`auto` / `middle` / `off`) |
| Correção de inclinação | nitidez do perfil de projeção, pesquisa de grosseira a fina até 0,01°, rotação bilinear; ou um ângulo manual |
| Caixa de conteúdo | blocos de tinta → dilatação → componentes conexos; poeira e sombras da borda do scanner rejeitadas, números de página mantidos |
| Margens / tamanho | margens em mm, tamanho de página fixo opcional com o conteúdo centrado; tudo o que fica fora da caixa de conteúdo é repintado com a cor do papel |
| Análise | tudo é medido numa cópia a ≈150 dpi (uma digitalização a 600 dpi é analisada em 1/16 dos pixéis); o resultado é mapeado de volta para a resolução completa |
| Dewarp | as linhas de texto são seguidas através de tiras verticais estreitas (picos do perfil de linhas encadeados de tira em tira); a ondulação de cada linha em torno da sua própria altura média torna-se um campo de reamostragem vertical, interpolado entre linhas; ignorado, a menos que várias linhas longas mostrem uma curvatura nítida |
| Iluminação | `--normalize`: cor do papel por canal a partir de uma cópia a ≈60 dpi com filtro de máximo e desfocada, depois um ganho por pixel |
| Binarização | Sauvola (predefinição), Wolf, Niblack, NICK, Bradley, Otsu, **auto** (por página: experimenta os métodos locais numa cópia a ≈150 dpi, mantém o que tem menos pontinhos isolados e uma proporção de tinta plausível), todos a partir de somas de colunas deslizantes com memória O(largura) |
| Limpeza | `--invert` (negativos: mediana escura + cauda clara), `--auto-levels` (alongamento 0,5 %/99,5 %, um só ganho para todos os canais), `--dropout red|green|blue`, `--punch-holes` (manchas redondas escuras de 3–10 mm junto à borda, preenchidas com a cor do papel circundante), `--fingers` (regiões da cor da pele que tocam a borda, avaliadas em relação à cor do papel), `--remove-lines` (traços ≥ 25 mm e ≤ 1,2 mm de espessura; as hastes de glifos que cruzam uma linha sobrevivem), `--sharpen` (máscara de nitidez ≈0,3 mm), `--despeckle-strength` |
| Imagens | blocos com elevada proporção de meios-tons (o texto é bimodal, as fotografias são contínuas) ou áreas escuras sólidas, fechados e filtrados por tamanho → manchas a cores |
| Saída | cor, cinzento, P/B, **mixed** (texto de 1 bit + manchas a cores) ou **hybrid** (+ camada de fundo de baixa resolução); redução de amostragem opcional para `--output-dpi`; tamanho de página fixo ou uniforme em todo o livro com alinhamento |
| PDF | escritor próprio: JPEG (cor/cinzento), CCITT Group 4 para 1 bit (recorre a Flate quando é menor), páginas em camadas (máscara de stencil + fundo + manchas); tamanho de página verdadeiro a partir do DPI |
| Imagens (ficheiros) | PNG com resolução, TIFF Group 4 para preto e branco |
| Problemas do papel | `--show-through` (nivela a iluminação e depois puxa de volta para o papel os pixéis apenas ligeiramente mais escuros do que ele; a tinta verdadeira não é tocada), `--descreen` (blocos de ≈2 mm que são sobretudo meios-tons e agitados à escala do pixel são ligeiramente desfocados; os blocos de texto ficam intactos) |
| Folhas separadoras | `--split-on-barcode` (páginas com um código de barras, na vertical, viradas 180° ou de lado, lido na digitalização em bruto — Code 128, EAN-13, ITF, Code 39 —, iniciam um novo documento com o nome do código → `book_001_ACT-17.pdf`), `--make-separator TEXT` imprime uma folha dessas (PNG A4) |
| Navegação no PDF | `--bookmarks` (uma entrada de índice por ficheiro de origem), `--front-matter N` (páginas i, ii, iii … depois 1, 2, 3 nos leitores de PDF) |
| Apagar zonas | `--erase X,Y,W,H` (mm a partir do canto superior esquerdo da página, repetível): pintado com a cor do papel antes de qualquer outra medição; `erase=` nos projetos `.lgr`; campo de texto na GUI |
| Rotação manual | na GUI, uma folha virada com os botões de rotação (ou ±45°) fica bloqueada: a orientação automática (verificação incorporada, Tesseract OSD) não é aplicada por cima, mesmo a 0°; Reset devolve-a. Nos projetos: `orient-locked = 1` |
| Área de trabalho e linha de corte | `--work-area X,Y,W,H` (mm da digitalização carregada): tudo o que fica fora é pintado com a cor do papel antes de qualquer medição; `--cut-at FRACTION` corta uma folha de duas páginas nessa fração da sua largura em vez de na goteira ou no meio (qualquer rotação; numa folha virada 90° ou 270° as duas páginas saem uma por cima da outra). Na GUI ambas são desenhadas ou arrastadas sobre o original ("Work area", "Cut line"); `work =` e `split-at =` nos projetos `.lgr`. Testado apenas em folhas sintéticas `--cut-angle GRAUS` inclina a linha de corte (±20°, no sentido horário): cada página fica com o seu lado da linha oblíqua e o outro lado é pintado com a cor do papel (`cut-angle =` nos projetos). |
| Trapézio e tamanhos de papel | `--keystone-v PERCENTAGEM` / `--keystone-h PERCENTAGEM` (±30) endireitam à mão uma folha fotografada em ângulo, antes do corte (`keystone = v, h` nos projetos; as zonas desenhadas na folha são eliminadas, as linhas guia acompanham); `--page-size` aceita também `a2`–`a6`, `b3`–`b6`, `letter`, `legal`, `tabloid`. Na janela: cursores na barra da página e uma lista de tamanhos mais longa; o botão **Auto trapez** mede cada página após o corte (inclinação das linhas, largura do texto em cima e em baixo) e guarda uma correção só para essa página (`pageN.page_keystone = v, h`). Testado em folhas sintéticas; não em páginas reais tortas |
| Definições de uma página | Num projeto, `page1.CHAVE = VALOR` / `page2.CHAVE = VALOR` sob `[sheet]` dão à página esquerda (ou única) e à direita de uma folha cortada valores próprios de saída e limpeza (`mode`, `despeckle`, `content_adjust`, …; as mesmas chaves das definições globais de um projeto guardado com `--save-project`). Na janela: «Definições para: todas as páginas / só esta página» por cima de Saída e Limpeza, e a moldura verde do conteúdo altera só a página onde é arrastada. Experimentado em folhas sintéticas e em testes unitários; não à mão numa janela Um clique numa página processada seleciona-a (moldura azul); modo de saída, limpeza, trapézio, caixa e lápis OCR atuam só nela; as zonas OCR desenhadas guardam-se como `pageN.page_ocr_zones` / `pageN.page_ocr_ignore`. |
| Zonas OCR | `--ocr-zone X,Y,W,H[=IDIOMA][#table]` lê o OCR só no retângulo (mm na página processada; `#table` = um só bloco, linha a linha, para tabelas), `--ocr-ignore X,Y,W,H` salta uma zona (carimbo, cabeçalho). Na janela, três lápis nas páginas processadas: verde = zona OCR, vermelho = ignorar, violeta = tabela; clique direito apaga. Testado com um motor simulado; não à mão numa janela |
| Lote | `--skip-duplicates` (páginas consecutivas com uma diferença de miniatura 96×128 ≤ 2/255), `--split-on-blank` (páginas em branco separam documentos → `name_001.pdf`, …), `--target-size MB` (qualidade JPEG escolhida a partir de uma amostra de páginas para que o PDF caiba) |
| Entrada para OCR | páginas abaixo de 250 dpi são ampliadas ×2–×4 (Catmull-Rom) antes do Tesseract; as caixas de palavras são mapeadas de volta |
| Fotografias de telemóvel | `--perspective`: encontra a página como o grande quadrilátero claro (Otsu + cantos extremos, com verificações de convexidade/preenchimento) e deforma-a com uma homografia; não faz nada em digitalizações direitas ou de quadro inteiro |
| Controlo de qualidade e arquivo | `--report r.html` (folha de contactos, assinala páginas em branco / de tamanho atípico / muito inclinadas), `--multitiff out.tif` (TIFF Group 4 de várias páginas, apenas preto e branco) |
| Entrega | `--checksums` escreve `SHA256SUMS.txt` (mesmo formato que `sha256sum`) ao lado do PDF para cada ficheiro escrito; `--verify-sums SHA256SUMS.txt` volta a verificá-los mais tarde (saída 1 em qualquer divergência ou ficheiro em falta); `--rights-notice "…"` guarda uma declaração de direitos (XMP `dc:rights` com `--pdfa`, caso contrário a chave de informação `/Rights` e um ícone de nota na página 2); `--txt-each` escreve `<nome do pdf>.txt` ao lado do PDF para indexadores como DocFetcher / Agent Ransack; `--package FOLDER`, `FILE.zip` ou `FILE.iso` (ISO 9660 + Joliet, legível em Windows / macOS / Linux; sem Rock Ridge nem dados de arranque; ficheiros até 4 GiB) reúne tudo o que foi escrito mais `SHA256SUMS.txt` e um `MANIFEST.txt` para entrega (nunca substitui; zip limitado a 3 GiB); `--package-password-file FILE` (ou `-` com `LEGATOROCR_PACKAGE_PASSWORD`) cifra um pacote `.zip` com WinZip AES-256; `--audit-log FILE` acrescenta um registo JSON Lines por ficheiro escrito (hora, versão da ferramenta, entradas, SHA-256, tamanho) com `--retain-until YYYY-MM-DD` e `--legal-hold` opcionais – regista provas e não apaga nada |

O título é o primeiro título do texto OCR, salvo indicação em contrário; os erros de OCR viajam com o texto |
| Nitidez | `--measure-edge IMAGE [--edge-roi X,Y,W,H] [--dpi N]`: MTF50 / MTF10 a partir de um bordo oblíquo preto / branco numa digitalização ou alvo de teste. Apenas o bordo: sem deteção de alvo, medição de cor ou de ruído, sem classificação FADGI |
| Servidor MCP | `legatorocr --mcp` fala o Model Context Protocol em stdin/stdout, para que um assistente de IA possa chamar `scan_to_pdf`, `pdf_toolbox`, `efactura`, `measure_edge` e `search`. O assistente obtém, através destas ferramentas, o acesso a ficheiros da sua conta; só o inicie para um cliente em que confie. Fala as revisões de protocolo 2024-11-05 e 2026-07-28 (escolhidas por pedido; a mais recente sem `initialize`, com `server/discover`); não experimentado com o Claude Desktop. Experimentado com o cliente Python MCP oficial (SDK 2.3.0), não com o Claude Desktop |
| Redação (ocultação) | `--redact email,phone-ro,iban-ro,cui,date` ou `--redact-regex RE` com `--ocr --format none`: as palavras correspondentes são pintadas de preto na página e removidas da camada de texto e das exportações de texto. Só se encontra o que o OCR leu, por isso veja o resultado antes de o entregar |
| Formulários preenchíveis | `--form-fields` com `--pdf`: caixas com linhas, caixas de seleção e sublinhados de um formulário em papel digitalizado tornam-se campos de PDF preenchíveis sobre a digitalização. Experimentado num formulário de teste renderizado, não em formulários digitalizados reais; os campos chamam-se field_N, não segundo as etiquetas impressas |
| Binarização por OCR | `--binarize-by-ocr` (com `--ocr`, modos preto e branco): cada página é lida com o limiar escolhido e com Otsu, mantém-se a versão de que o Tesseract tem mais confiança. Em 12 páginas romenas reais: 5438 -> 5245 erros de caracteres (-3,5 %); cerca do dobro do tempo para páginas com menos de 93 % de confiança |
| Nova tentativa em páginas duvidosas (não recomendado) | `--auto-retry` (com `--ocr`; `--auto-retry-below FRACTION`): uma página cuja leitura de volta parece duvidosa é processada de novo com outros binarizadores / correção de inclinação invertida / outro dpi de OCR e mantém-se a alternativa com a melhor pontuação ao estilo certify; `--explain` diz qual ganhou. **Testado e rejeitado:** em 12 páginas reais não mudou nada com o limiar predefinido (2803 -> 2803 erros de caracteres) e +25 erros quando forçado em todas as páginas; em 8 páginas sintéticas degradadas aumentou os erros de 59 para 424 (uma página inclinada passou de 0 para 354 erros). Está desligado por omissão e mantido apenas como experiência; não espere benefício (ROADMAP 4.24) |
| Receção | `--ocr-cache DIR` (resultados de OCR memorizados por imagem de página e definições; uma nova execução salta o OCR das páginas inalteradas), `--watch DIR` (pasta quente: cada nova digitalização é processada quando deixa de crescer; `--pdf` precisa de `{name}`), `--burst` (fotografias de telemóvel ordenadas pela hora de captura EXIF, mantido o fotograma mais nítido de cada rajada; lista o que descartou), `--scan-active` (lista PDF com JavaScript, ações de arranque, ficheiros embebidos; um olhar estático, um resultado limpo não é garantia) |
| OCR | caixas de palavras do motor incorporado ou do Tesseract → camada de texto invisível (modo de renderização 3, tipo de letra Type0 sem glifos + ToUnicode, para que ăâîșț e qualquer Unicode se copiem/pesquisem corretamente) |

A exportação processa em lotes limitados (processar → OCR → escrever), de modo que um livro a cores de várias centenas de páginas
não tenha de caber em memória.

Crates: `legatorocr-core` (pipeline) · `-pdf` (escritor) · `-ocr` (escolha do motor, controlador do Tesseract, saída hOCR / JSON) · `-nocr` (motor de OCR incorporado) ·
`-engine` (orquestração de exportação partilhada) · `-cli` · `-gui` (egui/eframe).

Portões de qualidade: ver `FUZZING.md` (10 suites de fuzz/propriedades, executadas semanalmente no CI com verificações cruzadas qpdf/poppler).

## Exportação de passagens

`--passages-jsonl FILE` (com `--ocr`) escreve JSON Lines: UTF-8, um objeto por linha, uma linha por
parágrafo de cada página mantida, páginas pela ordem de saída, parágrafos na ordem de leitura do motor (numa
página de duas colunas as caixas das duas colunas são por isso listadas coluna a coluna e podem
sobrepor-se). Os parágrafos são os que `--docx` usa (`words_to_paragraphs`), não uma segunda
deteção. Todas as chaves estão sempre presentes; um valor desconhecido é `null`.

| Chave | Tipo | Significado |
|---|---|---|
| `schema` | cadeia | sempre `"legatorocr.passage/1"` |
| `passage_id` | cadeia, 16 hex em minúsculas | primeiros 16 dígitos do SHA-256 de `"<page_image_sha256>:x0,y0,x1,y1"` (os números de `bbox_px`); a mesma imagem de página e a mesma caixa dão sempre o mesmo id, único no ficheiro |
| `source_file` | cadeia | nome de ficheiro da entrada (com `#N` para a página N de uma entrada de várias páginas) |
| `page` | inteiro >= 1 | número da página na saída (após remoção de páginas em branco e duplicadas; uma folha dupla dividida conta duas) |
| `page_label` | cadeia ou `null` | número de página impresso, apenas com `--page-labels` e apenas onde a sua regra de sequência etiquetaria a página do PDF; caso contrário `null` |
| `paragraph_index` | inteiro >= 0 | 0, 1, 2, ... dentro da página |
| `text` | cadeia, não vazia | o parágrafo; linhas separadas por `\n`, palavras por um espaço. Com `--clean-text` a limpeza é aplicada ao parágrafo, pelo que o texto é o que `--txt` mostra |
| `bbox_px` | 4 inteiros | `[x0, y0, x1, y1]` em pixéis da imagem da página de saída, origem no canto superior esquerdo, `x1`/`y1` exclusivos; `0 <= x0 < x1 <= page_width_px`, o mesmo para y |
| `bbox_frac` | 4 números | a mesma caixa dividida pela largura / altura da página, 6 casas decimais, dentro de 0..1 |
| `page_width_px`, `page_height_px` | inteiros | tamanho da imagem da página de saída |
| `language` | cadeia | a definição de idioma de OCR usada para a página (códigos do Tesseract como `ron+eng`, respeitando `--page-lang`); é a definição, não um idioma detetado |
| `mean_confidence` | número 0..100 ou `null` | média das confianças das palavras do motor no parágrafo, 2 casas decimais; `null` se nenhuma palavra a tiver |
| `page_image_sha256` | cadeia, 64 hex em minúsculas | SHA-256 dos bytes da imagem da página (ver `page_image_basis`) |
| `page_image_file` | cadeia ou `null` | nome dessa imagem dentro de `-o` quando foi escrita (`--format png/jpeg/tiff`); caso contrário `null` |
| `page_image_basis` | `"file"` ou `"png-encoding"` | `"file"`: o hash é do ficheiro de imagem escrito. `"png-encoding"` (com `--format none`): nenhuma imagem foi escrita; o hash é dos bytes PNG que `--format png` escreveria para esta página |
| `cite` | cadeia | `"<título> p.<etiqueta>"`: o título é `--passages-title` ou o nome do ficheiro de origem sem extensão; a etiqueta é `page_label`, senão `page` |

Verificar um ficheiro (apenas Python da biblioteca padrão): `python3 scripts/check-passages.py out.jsonl [--txt out.txt] [--images DIR]`.
Verifica todas as chaves e tipos, se cada caixa está dentro da sua página, as frações, o hash do id, a
forma de `cite` e, com `--images`, os hashes das imagens contra os ficheiros escritos; com `--txt`
compara as passagens de cada página com a mesma página da saída `--txt` (espaço em branco
colapsado) e imprime a percentagem de correspondência. O formato é próprio do LegatorOCR; se uma determinada
ferramenta de investigação (por exemplo o TEZAUR) o consegue importar, não foi verificado.

## Assistente de captura com telemóvel

`web/capture/index.html` é um único ficheiro HTML offline (sem pedidos externos, sem armazenamento, sem telemetria; inglês e romeno, cadeias de texto num só objeto). Abra-o num telemóvel (a câmara precisa de https ou localhost na maioria dos navegadores; `file://` funciona em alguns), inicie a câmara, pouse a página numa superfície mais escura. Ele encontra a página clara (limiar de Otsu, maior região conexa, cantos por x+y / x-y extremos, portanto até cerca de 45 graus de rotação), desenha o contorno e dispara sozinho quando o contorno esteve parado durante 0,8 s e a página passa as verificações; caso contrário diz porquê: nenhuma página encontrada, página não totalmente visível, demasiado desfocada (variância do Laplaciano), demasiado escura, demasiado clara. Um botão manual, uma tira de miniaturas com eliminação e "Save burst as ZIP" (ZIP armazenado, escrito à mão) dão `burst-YYYYMMDD-HHMMSS.zip` com `page-0001.jpg`, `page-0002.jpg`, ... à resolução do fluxo da câmara (um fotograma de vídeo, não necessariamente a resolução total de fotografia do sensor). Cada JPEG leva uma hora de captura EXIF, pelo menos 4 s depois da anterior, para que `legatorocr --burst` (predefinição `--burst-gap 3`) mantenha a ordem e não tome duas páginas por uma só rajada. Depois: `legatorocr --burst --pdf book.pdf page-*.jpg`.
Testado apenas em fotogramas **sintéticos** no Chromium sem interface com uma câmara falsa (`scripts/test-capture-assistant.py`): erro de canto de 1,0-2,1 px a 640 de largura em 6 posicionamentos (rotação de -14 a +31 graus, deslocamentos, uma distorção trapezoidal), as recusas disparam com o motivo certo, o ZIP passa `zipfile.testzip` e `unzip -t`, e `--burst` aceita as páginas descomprimidas. **Não testado:** telemóveis reais, iluminação e sombras reais, desfocagem de movimento, focagem automática, iOS Safari, uma secretária clara ou branca (a página funde-se então com o fundo), a recusa "demasiado clara". Todos os limiares são estimativas não afinadas.

## Indícios de integridade (`--integrity-hints`)

**Risco ELEVADO de falsos alarmes. Leia isto antes de usar.** `--integrity-hints FILE.json` (opcional, executa-se nas imagens de entrada tal como estão, antes de qualquer limpeza) escreve, por página, caixas em pixéis da página que uma pessoa pode querer voltar a examinar, cada uma com um "o que significa" e "causas inocentes comuns" em linguagem simples. É uma lista de coisas *a verificar*, nunca um veredicto; a saída não diz que um documento é genuíno ou não. Não a use como única base de qualquer decisão sobre uma pessoa ou o diploma de uma pessoa; pergunte à instituição emissora.

Sinais (`--integrity-signals LIST`; `all`, `default`, ou nomes):

| Sinal | Observa | Executa-se por omissão |
|---|---|---|
| `copy_move` | blocos 16x16 idênticos (com hash; papel em branco e glifos repetidos mais do que algumas vezes ignorados) em dois locais, a qualquer deslocamento de pixéis; caixas de pelo menos 64 px em ambos os lados | **sim** |
| `jpeg_grid` | entradas JPEG: uma janela de 128 px cujo padrão de bordas de blocos 8x8 está deslocado em relação ao resto da página | não: 4 de 12 páginas não editadas assinaladas, 0 de 60 edições encontradas |
| `jpeg_double` | entradas JPEG: padrão em pente de uma segunda gravação (a estatística de `--verify-document`, página inteira) | não: sem falso alarme, mas 0 de 60 páginas editadas assinaladas no teste abaixo |
| `noise` | blocos cujo ruído fino é 3x a mediana da página | não: 10 de 12 páginas não editadas assinaladas |
| `line_size` | precisa de `--ocr`: uma palavra cuja altura ou posição está desalinhada com a sua linha de texto | não: 12 de 12 páginas não editadas assinaladas |

Medido apenas em edições **sintéticas** (12 páginas reais do conjunto de teste de OCR, JPEG q85; edições: uma cadeia de dígitos desenhada sobre uma palavra, um bloco de 220x140 copiado para outro sítio, um bloco de 260x180 de uma cópia q45 colado num deslocamento estranho, ruído gaussiano em 240x160; cada página editada gravada de novo a q85; e as páginas limpas gravadas uma vez, regravadas uma vez a q85, regravadas outra vez a q75; `docs/experiments/integrity_eval.py`, ROADMAP 7.5c). `copy_move`: encontrou 10 de 12 blocos copiados, 0 de 36 páginas não editadas/regravadas assinaladas; **não** encontra um dígito ou uma palavra redigitados, e falha blocos menores que 64 px. O limite de tamanho foi fixado depois de ver falsos alarmes nas mesmas páginas, pelo que esse valor é otimista. Estes números nada dizem sobre falsificações reais, que são feitas com outras ferramentas, outros tipos de letra e outra compressão; carimbos reais, logótipos repetidos e papéis timbrados não estavam no teste e são a fonte esperada de falsos alarmes. Os outros sinais estão disponíveis com `--integrity-signals all` apenas para investigação.

## Limites conhecidos

Veja `COMPARISON.md` para o que outras ferramentas fazem e esta não. Em resumo:

- **Orientação**: o teste incorporado só encontra "a página está deitada de lado", não *para que lado*. A **orientação por OCR**
  (interruptor da GUI / `--auto-rotate`) resolve 90° vs 270° e páginas de pernas para o ar: com os dados `osd` do Tesseract quando
  instalados, caso contrário com o motor incorporado, que lê uma cópia reduzida nas quatro rotações e mantém aquela cujas
  palavras são encontradas nas listas de palavras do idioma (precisa de cerca de uma dúzia de letras de texto impresso; caso contrário a página fica
  como está). Alternativa manual: *Rotate left/right 90°* / `--rotate`.
- Zonas de apagar: escritas em milímetros (iguais em todas as páginas) ou desenhadas com o rato por folha (arraste na vista Original, o clique direito remove; guardadas no projeto); as zonas de imagem desenham-se da mesma maneira (azul); as linhas-guia de dewarp também (à mão livre, tipo *Guide line*; também escritas por `--dewarp-guide` / campo da GUI). O desenho na GUI não foi testado visualmente.
  As imagens são também detetadas automaticamente
  (sensibilidade ajustável) e a caixa de conteúdo pode ser empurrada por página (campos numéricos ou arrastando os seus bordos verdes na GUI; numa folha dupla dividida o ajuste aplica-se às duas páginas).
- O dewarp corrige apenas a curvatura vertical das linhas de texto (sem perspetiva / esticamento horizontal).
- `--pdfa` escreve a *estrutura* PDF/A-2b (tipo de letra de texto TrueType embebido sem glifos, pacote XMP coincidente com o dicionário Info, perfil de intenção de saída sRGB embebido, cinzento baseado em CIE, ID do trailer). O tipo de letra, o perfil ICC e o XMP foram verificados com fontTools, LittleCMS e um analisador de XML, e o ficheiro com qpdf e poppler, e o trabalho de CI `PDF/A validation` executa o veraPDF (greenfield 1.30.x, perfil PDF/A-2b) sobre ficheiros de exemplo gerados — preto e branco, mixed, hybrid, cinzento, com e sem camada de OCR, uma e duas páginas — e falha quando algum é rejeitado. Isso é um teste dessas amostras, **não uma certificação** de todas as saídas possíveis. Entrada PDF: descodificação de Huffman JBIG2 verificada contra o pdfium em fluxos gerados (a variante de bitmap coletivo MMR apenas contra o nosso próprio descodificador G4, o pdfium renderiza-a em branco); refinamento/agregação de Huffman (refinamento de região de texto, símbolos refinados e agregados; tabelas personalizadas) verificado contra o poppler e, exceto para deslocamentos de refinamento RDW/RDH além de -2..1, o pdfium (o pdfium centra a referência com RDW>>2 em vez de RDW>>1 em regiões de texto de Huffman, e descodifica mal o caso de igual tamanho e deslocamento zero; o poppler e o nosso descodificador seguem a norma), com símbolos refinados vazios em dicionários agregados de Huffman recusados; os estilos de bloco de código JPEG 2000 incl. bypass/termall, POC, PPM e PPT foram verificados contra o OpenJPEG 2.5 em cerca de 1350 fluxos gerados (sem perdas exato, 9/7 dentro de 2 níveis de cinzento; os fluxos PPM/PPT foram produzidos reescrevendo os do OpenJPEG, que o OpenJPEG depois descodificou de forma idêntica), paletas JPEG 2000 e o estilo de bloco de código de alto débito (Parte 15) não suportados, a predição típica JBIG2 para regiões de refinamento (TPGRON) e as grelhas de meios-tons deslocadas verificadas apenas contra o nosso próprio codificador (o poppler descodifica-as de forma diferente); ficheiros cifrados: as palavras-passe de utilizador e de proprietário foram verificadas contra ficheiros feitos com qpdf (RC4-40/128, AES-128, AES-256 R5/R6); códigos de barras: Code 128 (conjuntos A/B/C), EAN-13, ITF, Code 39 são lidos, só o Code 128 é impresso. JBIG2 e Group 3 foram verificados contra a saída do poppler / libtiff; a composição de páginas em camadas apenas contra páginas do nosso próprio escritor.
- A correção de perspetiva precisa de uma página claramente mais clara do que o que a rodeia e que mostre os quatro cantos; caso contrário deixa a fotografia em paz. Não desenrola páginas curvas (use `--dewarp`).
- A remoção de pele/furos/dedos são heurísticas: `--fingers` está desligado por omissão e pode comer fotografias de tons de pele na borda da página.
- O DPI é lido dos cabeçalhos PNG/JPEG (150–1200 dpi; 50–149 apenas quando o tamanho de página implícito é plausível, e nunca 72/96, que os editores escrevem por omissão) mas não dos cabeçalhos TIFF: defina `--dpi` à mão em caso de dúvida; o TIFF de 16 bits é reduzido a 8 bits.
- Inclinação: páginas com quase nenhuma tinta ficam como estão, e quando as linhas de texto e a estrutura vertical dão ambas um ângulo claro mas diferente (desenhos oblíquos, tramas) a página não é rodada. As páginas que já são únicas e direitas devem ser processadas com `--split off`.
- Uma margem escura do leito do scanner *a tocar* o texto pode ainda aumentar a caixa de conteúdo detetada
  (margens e sombras de canto separadas do texto são removidas).
- As compilações para Windows e macOS vêm dos fluxos de trabalho de CI (`.github/workflows`); o ambiente de desenvolvimento
  do autor verificou apenas Linux.
- Releases: **Actions → Release → Run workflow** (introduza uma etiqueta como `v0.2.0-pre.1`), ou faça push de uma etiqueta `v*`.
  O fluxo de trabalho executa primeiro toda a matriz de CI, depois compila as cinco plataformas e abre uma
  pré-release em **rascunho** para revisão; nada é publicado até carregar em Publish.
