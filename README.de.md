# LegatorOCR

[English](README.md) · [Română](README.ro.md) · [Français](README.fr.md) · [Italiano](README.it.md) · [Español](README.es.md) · [Português](README.pt.md) · **Deutsch** · [Magyar](README.hu.md)

Version: 0.2.0-pre.43 · Letzte Aktualisierung: 2026-11-10

Präsentationsseite: <https://legatorocr.chiuta.ro> (Quellcode in `docs/`).

Unabhängig implementierte Nachbearbeitung in Rust für gescannte Bücher:
**teilen → Schräglage korrigieren → zuschneiden → Ränder → bereinigen / binarisieren → PDF mit durchsuchbarer OCR-Textebene.**
Derselbe *Arbeitsablauf* wie bei klassischen Scan-Tailoring-Werkzeugen, aber unabhängiger Code. Grafische Oberfläche
(Windows, macOS, Linux) und Kommandozeile.

## Schnellstart

**GUI** — `legatorocr-gui` starten (unter macOS `LegatorOCR.app` öffnen). Scans oder einen Ordner ins
Fenster ziehen (oder *Add*), rechts die Einstellungen wählen, die Vorschau **Side by side / Original / Processed**
prüfen, einzelne Seiten anpassen (drehen, Seite teilen, manuelle Schräglage) und dann **Export PDF…** oder
**Export images…** wählen. Die Einstellungen bleiben zwischen den Sitzungen erhalten; **File → Save project…** speichert die Seitenliste samt
Einzelseiten-Anpassungen (Drehung, Teilung, Schräglage, Korrektur des Inhaltsrahmens) in einer Klartext-Datei `.lgr`.
Sprachen (folgen der Systemsprache; Umschaltung im Menü): Română, English, Français, Italiano,
Español, Português, Deutsch, Magyar.

**Videotour durch das Fenster** — 11 Clips ohne Ton (insgesamt etwa 14 Minuten, Untertitel in acht Sprachen), die jede Funktion der grafischen Oberfläche durchgehen: [docs/video/gui/](docs/video/gui/) oder der Abschnitt *Fenster-Rundgang* auf der [Projektseite](https://legatorocr.chiuta.ro/). Aufgenommen unter Linux mit erzeugten Beispielscans und englischer Oberfläche; das Ziehen von Dateien ins Fenster wird nur beschrieben, nicht gezeigt.

**CLI**

```
legatorocr scan_*.png --mode bw --dpi 300 --margin 6 --page-size a5 \
    --pdf carte.pdf --ocr --lang ron+eng
```

Ausgabemodi: `--mode color|gray|bw|mixed|hybrid`. **mixed** = scharfer 1-Bit-Text plus automatisch gefundene farbige Bildflächen; **hybrid** = dasselbe über einem niedrig aufgelösten Papierhintergrund
(`--hybrid-dpi`), was farbige Buchseiten von etwa 60–100 KB statt 700 KB+ ergibt.
Weitere: `--threshold sauvola|wolf|niblack|nick|bradley|otsu`, `--normalize` (Beleuchtung ausgleichen),
`--dewarp` (gekrümmte Zeilen begradigen), `--dewarp-guide "X,Y X,Y …"` (Sie geben die gebogene Linie als Punkte an, Bruchteile 0–1 der entzerrten Seite; wiederholbar; ersetzt die automatische Schätzung), `--output-dpi N`, `--uniform-size`, `--align top-left`,
`--project FILE.lgr` / `--save-project FILE.lgr`. Mehrseitige TIFFs werden Seite für Seite gelesen
(`scan.tif#3` adressiert eine Seite).

`--skip-blank`, `--skew DEG` (feste Korrektur), `--rotate 90`, `--pdf-quality N` (0 = verlustfrei),
`--format png|jpeg|tiff|none`, `--tessdata DIR`, `--psm N`, `--min-conf N`, `--keep-going` (nicht lesbare
Eingaben überspringen, Exit-Status 2) — siehe `legatorocr --help`. Statt Dateien kann ein Ordner angegeben werden. Die Auflösung wird
aus dem PNG/JPEG-Header gelesen, wenn dieser 150–1200 dpi angibt (sonst 300; mit `--dpi` überschreibbar); die
EXIF-Drehung von Kameras wird angewendet und Transparenz auf Weiß reduziert. Zahlen außerhalb des zulässigen Bereichs werden
mit einer klaren Meldung abgelehnt, statt absurde Seitengrößen zu erzeugen.

## Weniger gebräuchliche Optionen

`-o, --out-dir DIR` Ordner für die verarbeiteten Seitenbilder · `--no-deskew`, `--max-skew DEG`, `--no-auto-orient`
(seitlich liegende Seiten), `--no-despeckle` (Flecken behalten) · `--sauvola-k K` (Schwarzweiß-Empfindlichkeit),
`--picture-sensitivity 0-1` (mixed/hybrid) · `--jpeg-quality N` (mit `--format jpeg`) · PDF-Metadaten
`--subject`, `--keywords` · `--tesseract PATH` (externe Engine) · `--burst-gap SECONDS` (mit `--burst`),
`--fuse-max-shift PX` (mit `--fuse-frames`) · `--watch-interval SECONDS`, `--watch-skip-existing` (mit
`--watch`) · `--version`. `--project FILE.ScanTailor` öffnet ein ScanTailor-Projekt: Die Scan-Liste und die Drehung je Bild werden übernommen; Schräglage, Teilung und Inhaltsrahmen werden neu ermittelt (der Reader wurde nach der Beschreibung des Formats geschrieben und an einem von Hand erstellten Projekt getestet, nicht an Dateien aus jeder ScanTailor-Version).
Eine andere OCR-Engine lässt sich einbinden: `--engine tesseract --tesseract PROGRAM` akzeptiert jedes Programm, das die Tesseract-Kommandozeile versteht und dessen TSV zurückgibt (Vorlage und Vertrag: `docs/examples/external-ocr-engine.py`; ein generatives Modell kann dort Wörter erfinden, daher einen Menschen in der Schleife behalten). OCR-Geschwindigkeit und -Genauigkeit auf Ihren eigenen Seiten: `scripts/bench-real.py DIR` (Bilder mit je einer Referenz `NAME.txt`; `--partial` für Referenzen, die nur einen Teil einer Seite abdecken).
**ONNX-OCR-Brücke** (`scripts/engine-onnx.py`; Python mit onnxruntime, numpy, Pillow): betreibt ein PaddleOCR-PP-OCR-Layoutpaar (DB-Textdetektor, danach ein CTC-Erkenner) als diese externe Engine, sodass ein von Ihnen gewähltes Modell die OCR-Engine sein kann, ohne dass LegatorOCR Gewichte mitliefert. Die Modelle laden Sie selbst herunter, z. B. die PP-OCRv6-Erkennungs- und -Erkenner-Modelle aus der Modellliste von PaddleOCR, nach ONNX konvertiert (`pip install paddle2onnx`, dann `paddle2onnx --model_dir DIR --model_filename inference.pdmodel --params_filename inference.pdiparams --save_file det.onnx --opset_version 14`; oder ein fertiger ONNX-Export aus einem Modell-Hub), dazu das passende Zeichenwörterbuch (im Stil von `ppocr_keys_v1.txt`: ein Zeichen pro Zeile; die Brücke legt das CTC-Blank auf Klasse 0 und hängt die Leerzeichen-Klasse an, wie PaddleOCR es tut). Verwendung: `export LEGATOROCR_ONNX_DET=det.onnx LEGATOROCR_ONNX_REC=rec.onnx LEGATOROCR_ONNX_DICT=dict.txt`, dann `legatorocr scan.png --pdf out.pdf --ocr --engine tesseract --tesseract scripts/engine-onnx.py`. Einstellungen (Variable oder dasselbe Flag, `--onnx-det/-rec/-dict/-size/-rec-height/-thresh/-unclip/-space`): Detektorseite 960, Erkennerhöhe 48 (32 bei älteren Modellen), Schwelle 0,3, Unclip 1,5. Die Boxen sind achsenparallel, es gibt keinen gedrehten Text und keinen Orientierungsklassifikator; Wörter werden anhand der Leerzeichen-Klasse über den CTC-Zeitschritt getrennt (ungefähre Boxen); die Konfidenz ist die mittlere Spitzenwahrscheinlichkeit x 100. **Was geprüft ist:** nur die Verkabelung, mit winzigen synthetischen ONNX-Modellen (`scripts/test-engine-onnx.py`: Verdrahtung, Box-Koordinaten nach der Größenänderung, CTC-Dekodierung, TSV über die CLI). **Nicht geprüft:** die Erkennungsgenauigkeit mit echten PP-OCR-Modellen (an dem Ort, an dem dies geschrieben wurde, ließ sich keines herunterladen) und ob rumänische Diakritika (ă â î ș ț) richtig herauskommen: Das hängt vom gewählten Modell und Wörterbuch ab; prüfen Sie es auf Ihren eigenen Seiten mit `scripts/bench-real.py`, bevor Sie sich darauf verlassen. Wie jede Modell-Engine kann sie Text erfinden.
**docTR-Familie der ONNX-Brücke (ROADMAP 4.33)**: dasselbe Skript liest docTR/OnnxTR-Modelle, darunter den Erkenner mit rumänischem Kopf aus `tools/ocr-train/romanian_head.py` (ă ș ț Ă Ș Ț, zu einem eingefrorenen docTR-CRNN hinzugefügt). `scripts/get-romanian-doctr-models.sh [mobilenet|resnet] [DIR]` lädt die Originalmodelle aus den Release-Assets von OnnxTR auf GitHub herunter, baut den rumänischen Erkenner (`romanian_head.py splice`, benötigt python3 mit onnx) und gibt den genauen Befehl aus. Verwendung: `export LEGATOROCR_ONNX_FAMILY=doctr LEGATOROCR_ONNX_DET=DIR/db_mobilenet_v3_large-4987e7bd.onnx LEGATOROCR_ONNX_REC=DIR/crnn_mobilenet_v3_small_ro.onnx LEGATOROCR_ONNX_DICT=DIR/vocab_ro.txt` (oder `--onnx-family doctr` usw.), dann `legatorocr scan.png --ocr --engine tesseract --tesseract scripts/engine-onnx.py`. Der Detektor findet Wörter (Eingabe 1024x1024, Schwelle der Wahrscheinlichkeitskarte 0,3), jeder Wortausschnitt wird mit 32x128 gelesen, mit gierigem CTC-Dekodieren (Blank = letzte Klasse; `--onnx-dict` ist das Vokabular als ein einziger String), und das Skript gruppiert die Wörter selbst zu Zeilen und Spalten, sodass das TSV in Lesereihenfolge vorliegt. Gemessen über die echte CLI an 12 Seiten einer rumänischen Zeitschrift (ABBYY-Referenzen, nicht von Hand geprüft; 2 CPU-Kerne): db_mobilenet_v3_large + rumänisches crnn_mobilenet_v3_small, GOOD8-CER mit Diakritika 4,26 %, exakte Wort-Trefferquote 88,2 %, etwa 3,4 s pro Seite (die Option `resnet`: 3,67 %, 89,6 %, etwa 18 s pro Seite); Tesseract `ron` auf denselben Seiten 5,25 %, 91,3 %, 2,7 s pro Seite. Andere Schriften und Scans: nicht gemessen. Das gemessene Ergebnis in einem Satz: beim Zeichenfehler auf gleicher Höhe mit Tesseract für reine Textseiten (besser nur dort, wo Tesseract eine Illustration als Text liest), bei der Wort-Trefferquote dahinter, eine Zeitschrift, Referenzen nicht von Hand geprüft; siehe ROADMAP 4.36.
OCRmyPDF-Namen werden akzeptiert: `-l/--language`, `--force-ocr`, `--redo-ocr`, `--skip-text`, `--deskew` (ohne Wirkung, standardmäßig
aktiv), `--rotate-pages`, `--output-type pdf|pdfa|pdfa-1|2|3`, `-j/--jobs N`, `--sidecar FILE`, `--image-dpi`
(die Ausgabe wird mit `--pdf FILE` benannt; es gibt keine positionale Ausgabe). `scripts/check-options.py` listet jede Option auf, der Dokumentation oder ein Test fehlt.

## Installation

Laden Sie das Archiv für Ihre Plattform von der Releases-Seite herunter oder bauen Sie aus dem Quellcode:

```
cargo build --release          # target/release/legatorocr and legatorocr-gui
scripts/package.sh <target>    # e.g. x86_64-unknown-linux-gnu → dist/LegatorOCR-<ver>-<target>.tar.gz
```

| Plattform | Artefakt | Hinweise |
|---|---|---|
| Linux x86-64 / ARM64 | `.tar.gz` (+ `.desktop`) | benötigt OpenGL 2+ und X11 oder Wayland |
| Windows x86-64 | `.zip` | benötigt OpenGL 2+ (beliebiger GPU-Treiber; einfache RDP-Sitzungen haben es unter Umständen nicht) |
| macOS Apple-Silicon / Intel | `.zip` mit `LegatorOCR.app` | **nicht signiert**: erster Start per Rechtsklick → Öffnen, oder `xattr -dr com.apple.quarantine LegatorOCR.app` |

**OCR funktioniert sofort** mit der eingebauten nativen Engine (`legatorocr-nocr`, reines Rust, keine
Installation; `--engine native`). Sie liest die acht Oberflächensprachen mit einem Modell plus Wortlisten je Sprache. Ihr Modell wurde mit synthetischem Text trainiert und danach an echten gescannten Zeilen einer rumänischen Zeitschrift und eines Lehrbuchs von 1960 feinabgestimmt (die Scans befinden sich nicht in diesem Repository; Herkunft und offene Lizenzfragen: `docs/audit/assets-licences.md`): Auf sauberen und mäßig verschlechterten synthetischen
Seiten macht sie weniger als 1 % Zeichenfehler, aber echte Scans alter oder ungewöhnlicher Drucke können schlechter sein als
Tesseract. `--engine auto` (Standard) verwendet daher **Tesseract, wenn es mit den
angeforderten Sprachen installiert ist**, und fällt sonst auf die native Engine zurück; `--engine tesseract` erzwingt es.
Tesseract (als separates Programm ausgeführt; die App findet es im `PATH`):
`sudo apt install tesseract-ocr tesseract-ocr-ron` · `brew install tesseract tesseract-lang` ·
Windows: `winget install UB-Mannheim.TesseractOCR` (zum `PATH` hinzufügen).
Diese Paketnamen wurden am 2026-11-04 geprüft (`docs/audit/ocr-externals.md`): Debian 13 und Ubuntu 24.04 haben `tesseract-ocr` und `tesseract-ocr-ron`; Homebrew `tesseract` ist 5.5.4 mit nur `eng` und `osd`, und `tesseract-lang` enthält die *fast*-Modelle; das winget-Paket hinkt hinterher (5.4.0 von 2024-06). Die Datei `ron` aus `apt`/`brew` ist das kleine *fast*-Modell (etwa 2,4 MB, 2017); das *best*-Modell (9,6 MB, im selben Jahr, dieselbe Repository-Historie) ist ein manueller Download von `ron.traineddata` aus `tesseract-ocr/tessdata_best` in den tessdata-Ordner (`--tessdata DIR`). Welches der beiden Ihre Seiten besser liest, wurde hier nicht gemessen.
Die App sucht auch in den üblichen Installationsordnern (Homebrew `/opt/homebrew/bin`, `/usr/local/bin`,
`C:\Program Files\Tesseract-OCR`), sodass eine per Doppelklick gestartete App ohne Bearbeiten von `PATH` funktioniert.
Ohne Tesseract wird die native Engine verwendet (der OCR-Schalter bleibt aktiv). Ein Befehl für alle optionalen Helfer: `legatorocr --install-modules` (gibt die Befehle aus) und `legatorocr --install-modules --yes` (führt sie aus).
Ein Build **ohne das einkompilierte Erkennungsmodell** (zum Beispiel solange dessen Lizenz ungeklärt ist, `docs/audit/assets-licences.md`) ist `cargo build --release --no-default-features --features lexicon` (nur `--no-default-features` hinzufügen, um auch die Wortlisten wegzulassen); die gesamte Testsuite läuft auf diese Weise durch, `--doctor` meldet dann die native Engine als fehlend, und OCR benötigt Tesseract oder eine externe Engine.
`--auto-rotate` / das OSD-Kontrollkästchen benötigen zusätzlich `osd.traineddata` (Teil der Standardpakete).

## Pipeline

| Stufe | Methode (Standard-, Lehrbuchtechniken) |
|---|---|
| Orientierung | Energie der Zeilen-/Spaltenprofile um das Band des Zeilenabstands (0° gegenüber einer Vierteldrehung); optional Tesseract OSD für die genaue Richtung; oder `--rotate` |
| Seitenteilung | Bund = leerstes Spaltenband in der Mitte eines Querformat-Bogens (`auto` / `middle` / `off`) |
| Schräglagenkorrektur | Schärfe des Projektionsprofils, Suche von grob nach fein bis 0,01°, bilineare Drehung; oder ein manueller Winkel |
| Inhaltsrahmen | Tintenblöcke → Dilatation → zusammenhängende Komponenten; Staub und Scannerrand-Schatten werden verworfen, Seitenzahlen bleiben erhalten |
| Ränder / Größe | Ränder in mm, optional feste Seitengröße mit zentriertem Inhalt; alles außerhalb des Inhaltsrahmens wird in Papierfarbe übermalt |
| Analyse | alles wird auf einer Kopie mit ≈150 dpi gemessen (ein 600-dpi-Scan wird auf 1/16 der Pixel analysiert); das Ergebnis wird auf die volle Auflösung zurückgerechnet |
| Entzerrung (Dewarp) | Textzeilen werden über schmale vertikale Streifen verfolgt (Spitzen des Zeilenprofils, von Streifen zu Streifen verkettet); das Wackeln jeder Zeile um ihre eigene mittlere Höhe wird zu einem vertikalen Resampling-Feld, zwischen den Zeilen interpoliert; wird übersprungen, außer mehrere lange Zeilen zeigen eine deutliche Krümmung |
| Beleuchtung | `--normalize`: Papierfarbe je Kanal aus einer maximalgefilterten, weichgezeichneten Kopie mit ≈60 dpi, dann ein Verstärkungsfaktor pro Pixel |
| Binarisierung | Sauvola (Standard), Wolf, Niblack, NICK, Bradley, Otsu, **auto** (pro Seite: probiert die lokalen Methoden auf einer Kopie mit ≈150 dpi aus und behält diejenige mit den wenigsten isolierten Flecken und einem plausiblen Tintenanteil), alle aus gleitenden Spaltensummen mit O(Breite) Speicher |
| Bereinigung | `--invert` (Negative: dunkler Median + heller Ausläufer), `--auto-levels` (Dehnung 0,5 %/99,5 %, ein Verstärkungsfaktor für alle Kanäle), `--dropout red|green|blue`, `--punch-holes` (dunkle runde Flecken von 3–10 mm nahe dem Rand, mit der umgebenden Papierfarbe gefüllt), `--fingers` (hautfarbene Bereiche, die den Rand berühren, im Verhältnis zur Papierfarbe beurteilt), `--remove-lines` (Linien ≥ 25 mm und ≤ 1,2 mm Dicke; Buchstabenschäfte, die eine Linie kreuzen, bleiben erhalten), `--sharpen` (Unscharfmaske ≈0,3 mm), `--despeckle-strength` |
| Bilder | Kacheln mit hohem Anteil an Mitteltönen (Text ist bimodal, Fotos sind kontinuierlich) oder volle dunkle Flächen, geschlossen und nach Größe gefiltert → Farbflächen |
| Ausgabe | Farbe, Grau, S/W, **mixed** (1-Bit-Text + Farbflächen) oder **hybrid** (+ niedrig aufgelöste Hintergrundebene); optionale Herunterskalierung auf `--output-dpi`; feste oder buchweit einheitliche Seitengröße mit Ausrichtung |
| PDF | eigener Writer: JPEG (Farbe/Grau), CCITT Group 4 für 1 Bit (fällt auf Flate zurück, wenn dieses kleiner ist), geschichtete Seiten (Schablonenmaske + Hintergrund + Flächen); echte Seitengröße aus der DPI |
| Bilder (Dateien) | PNG mit Auflösung, TIFF Group 4 für Schwarzweiß |
| Papierprobleme | `--show-through` (gleicht die Beleuchtung aus, zieht dann Pixel, die nur wenig dunkler als das Papier sind, auf Papierfarbe zurück; echte Tinte bleibt unberührt), `--descreen` (Kacheln von ≈2 mm, die überwiegend Mitteltöne sind und im Pixelmaßstab unruhig, werden leicht weichgezeichnet; Textkacheln bleiben unangetastet) |
| Trennblätter | `--split-on-barcode` (Seiten mit einem Strichcode, aufrecht, um 180° gedreht oder seitlich, auf dem Rohscan gelesen — Code 128, EAN-13, ITF, Code 39 — beginnen ein neues Dokument, das nach dem Code benannt wird → `book_001_ACT-17.pdf`), `--make-separator TEXT` druckt ein solches Blatt (A4-PNG) |
| PDF-Navigation | `--bookmarks` (ein Gliederungseintrag pro Quelldatei), `--front-matter N` (Seiten i, ii, iii … dann 1, 2, 3 in PDF-Viewern) |
| Zonen löschen | `--erase X,Y,W,H` (mm von der oberen linken Ecke der Seite, wiederholbar): wird vor allem anderen Messen in Papierfarbe übermalt; `erase=` in `.lgr`-Projekten; Textfeld in der GUI |
| Drehung von Hand | in der GUI wird ein Bogen, der mit den Drehtasten (oder ±45°) gedreht wurde, gesperrt: Die automatische Orientierung (eingebaute Prüfung, Tesseract OSD) wird nicht zusätzlich angewendet, auch nicht bei 0°; Reset gibt sie zurück. In Projekten: `orient-locked = 1` |
| Arbeitsbereich und Schnittlinie | `--work-area X,Y,W,H` (mm des geladenen Scans): alles außerhalb wird vor jeder Messung in Papierfarbe übermalt; `--cut-at FRACTION` schneidet einen Zweiseitenbogen bei diesem Anteil seiner Breite statt am Bund oder an der Mitte (bei jeder Drehung; bei einem um 90° oder 270° gedrehten Bogen kommen die beiden Seiten übereinander heraus). In der GUI werden beide auf dem Original gezeichnet oder gezogen („Work area“, „Cut line“); `work =` und `split-at =` in `.lgr`-Projekten. Nur an synthetischen Bögen getestet `--cut-angle GRAD` neigt die Schnittlinie (±20°, im Uhrzeigersinn): jede Seite behält ihre Seite der schrägen Linie, die andere Seite wird mit der Papierfarbe übermalt (`cut-angle =` in Projekten). |
| Trapez und Papierformate | `--keystone-v PROZENT` / `--keystone-h PROZENT` (±30) richten ein schräg fotografiertes Blatt von Hand vor dem Schnitt gerade (`keystone = v, h` in Projekten; auf dem Blatt gezeichnete Zonen entfallen, Führungslinien folgen); `--page-size` kennt auch `a2`–`a6`, `b3`–`b6`, `letter`, `legal`, `tabloid`. Im Fenster: Schieberegler in der Seitenleiste und eine längere Formatliste; die Schaltfläche **Auto trapez** misst jede Seite nach dem Schnitt (Zeilenneigung, Textbreite oben und unten) und merkt sich eine Korrektur nur für diese Seite (`pageN.page_keystone = v, h`). Auf synthetischen Blättern getestet; nicht an echten verzogenen Seiten |
| Einstellungen einer Seite | In einem Projekt geben `page1.SCHLÜSSEL = WERT` / `page2.SCHLÜSSEL = WERT` unter `[sheet]` der linken (oder einzigen) und der rechten Seite eines geschnittenen Blatts eigene Ausgabe- und Bereinigungswerte (`mode`, `despeckle`, `content_adjust`, …; dieselben Schlüssel wie die globalen Einstellungen eines mit `--save-project` gespeicherten Projekts). Im Fenster: „Einstellungen für: alle Seiten / nur diese Seite“ über Ausgabe und Bereinigung, und der grüne Inhaltsrahmen ändert nur die Seite, auf der er gezogen wird. An synthetischen Blättern und in Unit-Tests erprobt; nicht von Hand in einem Fenster Ein Klick auf eine verarbeitete Seite wählt sie aus (blauer Rahmen); Ausgabemodus, Bereinigung, Trapezkorrektur, Rahmen und OCR-Stifte wirken dann nur auf sie; gezeichnete OCR-Zonen werden als `pageN.page_ocr_zones` / `pageN.page_ocr_ignore` gespeichert. |
| OCR-Zonen | `--ocr-zone X,Y,W,H[=SPRACHE][#table]` liest OCR nur im Rechteck (mm auf der verarbeiteten Seite; `#table` = ein einziger Block, Zeile für Zeile, für Tabellen), `--ocr-ignore X,Y,W,H` lässt eine Zone aus (Stempel, Kopfzeile). Im Fenster drei Stifte auf verarbeiteten Seiten: grün = OCR-Zone, rot = ignorieren, violett = Tabelle; Rechtsklick löscht. Mit einer simulierten Engine getestet; nicht von Hand in einem Fenster |
| Stapel | `--skip-duplicates` (aufeinanderfolgende Seiten mit einer Differenz der 96×128-Miniatur ≤ 2/255), `--split-on-blank` (leere Seiten trennen Dokumente → `name_001.pdf`, …), `--target-size MB` (JPEG-Qualität aus einer Stichprobe von Seiten gewählt, damit das PDF passt) |
| OCR-Eingabe | Seiten unter 250 dpi werden vor Tesseract ×2–×4 vergrößert (Catmull-Rom); Wortboxen werden zurückgerechnet |
| Handyfotos | `--perspective`: findet die Seite als großes helles Viereck (Otsu + extreme Ecken, mit Prüfungen auf Konvexität/Füllung) und entzerrt sie mit einer Homographie; tut nichts bei aufrechten oder bildfüllenden Scans |
| QC und Archiv | `--report r.html` (Kontaktbogen, markiert leere / größenabweichende / stark geradegerückte Seiten), `--multitiff out.tif` (mehrseitiges Group-4-TIFF, nur Schwarzweiß) |

## Passagen-Export

`--passages-jsonl FILE` (mit `--ocr`) schreibt JSON Lines: UTF-8, ein Objekt pro Zeile, eine Zeile pro
Absatz jeder behaltenen Seite, Seiten in Ausgabereihenfolge, Absätze in der Lesereihenfolge der Engine (auf
einer zweispaltigen Seite werden die Boxen der beiden Spalten daher spaltenweise aufgelistet und können
sich überlappen). Die Absätze sind dieselben, die `--docx` verwendet (`words_to_paragraphs`), keine zweite
Erkennung. Jeder Schlüssel ist immer vorhanden; ein unbekannter Wert ist `null`.

| Schlüssel | Typ | Bedeutung |
|---|---|---|
| `schema` | string | immer `"legatorocr.passage/1"` |
| `passage_id` | string, 16 Kleinbuchstaben-Hex | die ersten 16 Ziffern des SHA-256 von `"<page_image_sha256>:x0,y0,x1,y1"` (die Zahlen von `bbox_px`); dasselbe Seitenbild und dieselbe Box ergeben immer dieselbe ID, in der Datei eindeutig |
| `source_file` | string | Dateiname der Eingabe (mit `#N` für Seite N einer mehrseitigen Eingabe) |
| `page` | integer >= 1 | Seitenzahl in der Ausgabe (nach Entfernen leerer Seiten und Duplikate; ein geteilter Doppelbogen zählt zwei) |
| `page_label` | string oder `null` | gedruckte Seitenzahl, nur mit `--page-labels` und nur dort, wo ihre Laufregel die PDF-Seite beschriften würde; sonst `null` |
| `paragraph_index` | integer >= 0 | 0, 1, 2, ... innerhalb der Seite |
| `text` | string, nicht leer | der Absatz; Zeilen durch `\n` getrennt, Wörter durch ein Leerzeichen. Mit `--clean-text` wird die Bereinigung auf den Absatz angewendet, der Text ist also derselbe, den `--txt` zeigt |
| `bbox_px` | 4 integers | `[x0, y0, x1, y1]` in Pixeln des Ausgabeseitenbildes, Ursprung oben links, `x1`/`y1` exklusiv; `0 <= x0 < x1 <= page_width_px`, ebenso für y |
| `bbox_frac` | 4 Zahlen | dieselbe Box geteilt durch Seitenbreite / -höhe, 6 Dezimalstellen, innerhalb von 0..1 |
| `page_width_px`, `page_height_px` | integers | Größe des Ausgabeseitenbildes |
| `language` | string | die für die Seite verwendete OCR-Spracheinstellung (Tesseract-Codes wie `ron+eng`, unter Beachtung von `--page-lang`); es ist die Einstellung, keine erkannte Sprache |
| `mean_confidence` | Zahl 0..100 oder `null` | Mittelwert der Wortkonfidenzen der Engine im Absatz, 2 Dezimalstellen; `null`, wenn kein Wort eine hat |
| `page_image_sha256` | string, 64 Kleinbuchstaben-Hex | SHA-256 der Bytes des Seitenbildes (siehe `page_image_basis`) |
| `page_image_file` | string oder `null` | Name dieses Bildes innerhalb von `-o`, wenn es geschrieben wurde (`--format png/jpeg/tiff`); sonst `null` |
| `page_image_basis` | `"file"` oder `"png-encoding"` | `"file"`: Der Hash ist der der geschriebenen Bilddatei. `"png-encoding"` (mit `--format none`): Es wurde kein Bild geschrieben; der Hash ist der der PNG-Bytes, die `--format png` für diese Seite schreiben würde |
| `cite` | string | `"<title> p.<label>"`: Der Titel ist `--passages-title` oder der Name der Quelldatei ohne Endung; die Beschriftung ist `page_label`, sonst `page` |

Eine Datei prüfen (nur Python-Standardbibliothek): `python3 scripts/check-passages.py out.jsonl [--txt out.txt] [--images DIR]`.
Es prüft jeden Schlüssel und Typ, ob jede Box innerhalb ihrer Seite liegt, die Bruchteile, den ID-Hash, die
Form von `cite` und, mit `--images`, die Bild-Hashes gegen die geschriebenen Dateien; mit `--txt` vergleicht es
die Passagen jeder Seite mit derselben Seite der `--txt`-Ausgabe (Leerraum
zusammengezogen) und gibt den Prozentsatz der Übereinstimmung aus. Das Format ist LegatorOCRs eigenes; ob ein bestimmtes
Recherchewerkzeug (zum Beispiel TEZAUR) es importieren kann, wurde nicht geprüft.

## Assistent für die Handy-Aufnahme

`web/capture/index.html` ist eine einzige Offline-HTML-Datei (keine externen Anfragen, kein Speicher, keine Telemetrie; Englisch und Rumänisch, Zeichenketten in einem Objekt). Öffnen Sie sie auf einem Handy (eine Kamera braucht in den meisten Browsern https oder localhost; `file://` funktioniert in manchen), starten Sie die Kamera und legen Sie die Seite auf eine dunklere Unterlage. Sie findet die helle Seite (Otsu-Schwelle, größte zusammenhängende Region, Ecken über extremes x+y / x-y, also bis zu etwa 45 Grad Drehung), zeichnet die Umrisslinie und löst von selbst aus, wenn die Umrisslinie 0,8 s ruhig war und die Seite die Prüfungen besteht; andernfalls sagt sie, warum: keine Seite gefunden, Seite nicht vollständig sichtbar, zu unscharf (Varianz des Laplace-Operators), zu dunkel, zu hell. Eine manuelle Schaltfläche, ein Miniaturstreifen mit Löschen und „Save burst as ZIP“ (handgeschriebenes ZIP ohne Kompression) liefern `burst-YYYYMMDD-HHMMSS.zip` mit `page-0001.jpg`, `page-0002.jpg`, ... in der Auflösung des Kamerastroms (ein Videobild, nicht unbedingt die volle Standbildauflösung des Sensors). Jedes JPEG trägt eine EXIF-Aufnahmezeit, mindestens 4 s nach der vorigen, damit `legatorocr --burst` (Standard `--burst-gap 3`) die Reihenfolge behält und nicht zwei Seiten für eine Serie hält. Dann: `legatorocr --burst --pdf book.pdf page-*.jpg`.
Nur an **synthetischen** Bildern in Headless-Chromium mit einer Fake-Kamera getestet (`scripts/test-capture-assistant.py`): Eckenfehler 1,0–2,1 px bei 640 Breite an 6 Platzierungen (Drehung -14 bis +31 Grad, Verschiebungen, eine Trapezverzerrung), die Ablehnungen greifen mit dem richtigen Grund, das ZIP besteht `zipfile.testzip` und `unzip -t`, und `--burst` akzeptiert die entpackten Seiten. **Nicht getestet:** echte Handys, echte Beleuchtung und Schatten, Bewegungsunschärfe, Autofokus, iOS Safari, ein heller oder weißer Tisch (die Seite verschmilzt dann mit dem Hintergrund), die Ablehnung „zu hell“. Alle Schwellwerte sind ungetunte Schätzungen.

## Integritätshinweise (`--integrity-hints`)

**Hohes Risiko von Fehlalarmen. Lesen Sie dies, bevor Sie es verwenden.** `--integrity-hints FILE.json` (Opt-in, läuft auf den Eingabebildern, so wie sie sind, vor jeder Bereinigung) schreibt pro Seite Boxen in Seitenpixeln, die sich ein Mensch noch einmal ansehen möchte, jeweils mit einer allgemeinverständlichen Angabe, „was es bedeutet“, und „häufigen harmlosen Ursachen“. Es ist eine Liste von Dingen, die *zu prüfen* sind, niemals ein Urteil; die Ausgabe sagt nicht, ob ein Dokument echt ist oder nicht. Verwenden Sie es nicht als einzige Grundlage für irgendeine Entscheidung über eine Person oder das Diplom einer Person; fragen Sie die ausstellende Institution.

Signale (`--integrity-signals LIST`; `all`, `default` oder Namen):

| Signal | Betrachtet | Läuft standardmäßig |
|---|---|---|
| `copy_move` | identische 16x16-Blöcke (gehasht, leeres Papier und mehr als wenige Male wiederholte Glyphen ignoriert) an zwei Stellen, bei beliebigem Pixelversatz; Boxen von mindestens 64 px auf beiden Seiten | **ja** |
| `jpeg_grid` | JPEG-Eingaben: ein 128-px-Fenster, dessen 8x8-Blockkantenmuster gegenüber dem Rest der Seite versetzt ist | nein: 4 von 12 unbearbeiteten Seiten markiert, 0 von 60 Bearbeitungen gefunden |
| `jpeg_double` | JPEG-Eingaben: Kammmuster eines zweiten Speicherns (die Statistik von `--verify-document`, ganze Seite) | nein: kein Fehlalarm, aber 0 von 60 bearbeiteten Seiten im folgenden Test markiert |
| `noise` | Kacheln, deren feines Rauschen das 3-Fache des Seitenmedians beträgt | nein: 10 von 12 unbearbeiteten Seiten markiert |
| `line_size` | benötigt `--ocr`: ein Wort, dessen Höhe oder Position nicht zu seiner Textzeile passt | nein: 12 von 12 unbearbeiteten Seiten markiert |

Nur an **synthetischen** Bearbeitungen gemessen (12 echte Seiten aus dem OCR-Testsatz, JPEG q85; Bearbeitungen: eine über ein Wort gezeichnete Ziffernfolge, ein anderswohin kopierter Ausschnitt von 220x140, ein Ausschnitt von 260x180 aus einer q45-Kopie, an einem ungeraden Versatz eingefügt, gaußsches Rauschen in 240x160; jede bearbeitete Seite mit q85 neu gespeichert; und die sauberen Seiten einmal gespeichert, einmal mit q85 neu gespeichert, nochmals mit q75 neu gespeichert; `docs/experiments/integrity_eval.py`, ROADMAP 7.5c). `copy_move`: fand 10 von 12 kopierten Ausschnitten, 0 von 36 unbearbeiteten/neu gespeicherten Seiten markiert; es findet **keine** neu getippte Ziffer oder ein neu getipptes Wort, und es verfehlt Ausschnitte unter 64 px. Die Größengrenze wurde festgelegt, nachdem an denselben Seiten Fehlalarme aufgefallen waren, daher ist diese Zahl optimistisch. Diese Zahlen sagen nichts über echte Fälschungen, die mit anderen Werkzeugen, anderen Schriften und anderer Kompression angefertigt werden; echte Stempel, wiederholte Logos und Briefköpfe waren nicht im Test und sind die erwartete Quelle von Fehlalarmen. Die anderen Signale sind mit `--integrity-signals all` nur für die Forschung verfügbar.

## Bekannte Grenzen

Siehe `COMPARISON.md` dazu, was andere Werkzeuge können und dieses nicht. Kurz gesagt:

- **Orientierung**: Der eingebaute Test findet nur „Seite liegt auf der Seite“, nicht, *in welche Richtung*. Die **Orientierung per OCR**
  (GUI-Schalter / `--auto-rotate`) löst 90° gegenüber 270° und kopfstehende Seiten: mit den `osd`-Daten von Tesseract, wenn diese
  installiert sind, sonst mit der eingebauten Engine, die eine verkleinerte Kopie in allen vier Drehungen liest und diejenige behält, deren
  Wörter in den Wortlisten der Sprache gefunden werden (benötigt etwa ein Dutzend Buchstaben gedruckten Text; andernfalls bleibt die Seite
  unverändert). Manueller Ausweg: *Rotate left/right 90°* / `--rotate`.
- Löschzonen: in Millimetern eingegeben (auf jeder Seite gleich) oder mit der Maus pro Bogen gezeichnet (auf der Ansicht Original ziehen, Rechtsklick entfernt; im Projekt gespeichert); Bildzonen werden auf dieselbe Weise gezeichnet (blau); Dewarp-Führungslinien ebenso (freihändig, Art *Guide line*; auch eingegeben über `--dewarp-guide` / GUI-Feld). Das Zeichnen in der GUI wurde nicht visuell getestet.
  Bilder werden außerdem automatisch erkannt
  (Empfindlichkeit einstellbar), und der Inhaltsrahmen kann pro Seite nachjustiert werden (numerische Felder oder durch Ziehen seiner grünen Kanten in der GUI; bei einem geteilten Doppelbogen gilt die Verschiebung für beide Seiten).
- Dewarp korrigiert nur die vertikale Krümmung von Textzeilen (keine Perspektive / horizontale Streckung).
- `--pdfa` schreibt die *Struktur* von PDF/A-2b (eingebettete glyphenlose TrueType-Textschrift, XMP-Paket passend zum Info-Wörterbuch, eingebettetes sRGB-Ausgabe-Intent-Profil, CIE-basiertes Grau, Trailer-ID). Schrift, ICC-Profil und XMP wurden mit fontTools, LittleCMS und einem XML-Parser geprüft, die Datei mit qpdf und poppler, und der CI-Job `PDF/A validation` lässt veraPDF (greenfield 1.30.x, Profil PDF/A-2b) über erzeugte Beispieldateien laufen — Schwarzweiß, mixed, hybrid, Grau, mit und ohne OCR-Ebene, ein und zwei Seiten — und schlägt fehl, wenn eine abgelehnt wird. Das ist ein Test dieser Beispiele, **keine Zertifizierung** jeder möglichen Ausgabe. PDF-Eingabe: JBIG2-Huffman-Dekodierung gegen pdfium an erzeugten Strömen geprüft (die Variante mit kollektiver MMR-Bitmap nur gegen unseren eigenen G4-Dekoder, pdfium rendert sie leer); Huffman-Refinement/-Aggregation (Refinement von Textregionen, verfeinerte und Aggregat-Symbole; eigene Tabellen) gegen poppler und, außer bei Refinement-Offsets RDW/RDH jenseits von -2..1, gegen pdfium geprüft (pdfium zentriert die Referenz in Huffman-Textregionen mit RDW>>2 statt RDW>>1 und dekodiert den Fall gleicher Größe mit Offset null falsch; poppler und unser Dekoder folgen dem Standard), wobei leere verfeinerte Symbole in Huffman-Aggregat-Wörterbüchern abgelehnt werden; JPEG-2000-Code-Block-Stile einschließlich Bypass/Termall, POC, PPM und PPT wurden gegen OpenJPEG 2.5 an etwa 1.350 erzeugten Strömen geprüft (verlustfrei exakt, 9/7 innerhalb von 2 Graustufen; PPM/PPT-Ströme entstanden durch Umschreiben der von OpenJPEG erzeugten, die OpenJPEG dann identisch dekodierte), JPEG-2000-Paletten und der Code-Block-Stil mit hohem Durchsatz (Teil 15) nicht unterstützt, JBIG2-Typical-Prediction für Refinement-Regionen (TPGRON) und verschobene Halbton-Raster nur gegen unseren eigenen Encoder verifiziert (poppler dekodiert sie anders); verschlüsselte Dateien: Benutzer- und Besitzerpasswörter wurden gegen mit qpdf erzeugte Dateien geprüft (RC4-40/128, AES-128, AES-256 R5/R6); Strichcodes: Code 128 (Sätze A/B/C), EAN-13, ITF, Code 39 werden gelesen, nur Code 128 wird gedruckt. JBIG2 und Group 3 wurden gegen die Ausgabe von poppler / libtiff verifiziert; die Komposition geschichteter Seiten nur gegen Seiten unseres eigenen Writers.
- Die Perspektivkorrektur braucht eine Seite, die deutlich heller ist als ihre Umgebung und alle vier Ecken zeigt; andernfalls lässt sie das Foto unberührt. Sie rollt keine gewölbten Seiten aus (verwenden Sie `--dewarp`).
- Das Entfernen von Haut/Löchern/Fingern sind Heuristiken: `--fingers` ist standardmäßig aus und kann hautfarbene Fotos am Seitenrand verschlucken.
- Die DPI wird aus PNG/JPEG-Headern gelesen (150–1200 dpi; 50–149 nur, wenn die daraus folgende Seitengröße plausibel ist, und nie 72/96, was Editoren standardmäßig schreiben), aber nicht aus TIFF-Headern: Setzen Sie `--dpi` im Zweifel von Hand; 16-Bit-TIFF wird auf 8 Bit reduziert.
- Schräglage: Seiten mit fast keiner Tinte bleiben, wie sie sind, und wenn die Textzeilen und die vertikale Struktur beide einen deutlichen, aber unterschiedlichen Winkel liefern (schräge Zeichnungen, Schraffuren), wird die Seite nicht gedreht. Seiten, die bereits einzeln und gerade sind, sollten mit `--split off` verarbeitet werden.
- Ein dunkler Scannerrand, der den Text *berührt*, kann den erkannten Inhaltsrahmen weiterhin vergrößern
  (vom Text getrennte Ränder und Eckenschatten werden entfernt).
- Die Windows- und macOS-Builds stammen aus den CI-Workflows (`.github/workflows`); die Entwicklungsumgebung des Autors
  hat nur Linux verifiziert.
- Releases: **Actions → Release → Run workflow** (ein Tag wie `v0.2.0-pre.1` eingeben) oder ein `v*`-Tag pushen. Der Workflow führt zuerst die gesamte CI-Matrix aus, baut dann alle fünf Plattformen und öffnet ein
  **Entwurf**-Pre-Release zur Prüfung; nichts wird veröffentlicht, bis Sie auf Publish drücken.
