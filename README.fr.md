# LegatorOCR

[English](README.md) · [Română](README.ro.md) · **Français** · [Italiano](README.it.md) · [Español](README.es.md) · [Português](README.pt.md) · [Deutsch](README.de.md) · [Magyar](README.hu.md)

Version : 0.2.0-pre.44 · Dernière mise à jour : 2026-11-10

Site de présentation : <https://legatorocr.chiuta.ro> (sources dans `docs/`).

Post-processeur Rust indépendant pour livres numérisés :
**découpage → redressement → recadrage → marges → nettoyage / binarisation → PDF avec une couche de texte OCR interrogeable.**
Même *flux de travail* que les outils classiques de retouche de scans, code indépendant. Interface graphique
(Windows, macOS, Linux) et ligne de commande.

## Démarrage rapide

**Interface graphique** — lancez `legatorocr-gui` (ou ouvrez `LegatorOCR.app` sous macOS). Faites glisser des scans ou un dossier dans la
fenêtre (ou *Ajouter*), choisissez les réglages à droite, vérifiez l’aperçu **Côte à côte / Original / Traité**,
ajustez les pages une à une (rotation, découpage de page, inclinaison manuelle), puis **Exporter le PDF…** ou
**Exporter les images…**. Les réglages sont conservés d’une session à l’autre ; **Fichier → Enregistrer le projet…** conserve la liste des pages avec
les ajustements par page (rotation, découpage, inclinaison, correction de la zone de contenu) dans un fichier texte brut `.lgr`.
Langues (suivent la langue du système ; changement dans le menu) : Română, English, Français, Italiano,
Español, Português, Deutsch, Magyar.

**Visite vidéo de la fenêtre** — 11 clips muets (environ 14 minutes au total, sous-titres en huit langues) qui passent en revue chaque fonction de l’interface graphique : [docs/video/gui/](docs/video/gui/), ou la section *Visite de la fenêtre* de la [page du projet](https://legatorocr.chiuta.ro/). Filmés sous Linux avec des scans d’exemple générés et l’interface en anglais ; le glisser-déposer dans la fenêtre est seulement décrit, pas montré.

**Ligne de commande**

```
legatorocr scan_*.png --mode bw --dpi 300 --margin 6 --page-size a5 \
    --pdf carte.pdf --ocr --lang ron+eng
```

Modes de sortie : `--mode color|gray|bw|mixed|hybrid`. **mixed** = texte 1 bit net plus plages d’images en couleur
détectées automatiquement ; **hybrid** = la même chose sur un fond papier en basse résolution
(`--hybrid-dpi`), ce qui donne des pages de livre en couleur d’environ 60–100 Ko au lieu de 700 Ko et plus.
Aussi : `--threshold sauvola|wolf|niblack|nick|bradley|otsu`, `--normalize` (uniformiser l’éclairage),
`--dewarp` (redresser les lignes courbes), `--dewarp-guide "X,Y X,Y …"` (vous donnez la ligne courbe sous forme de points, fractions 0–1 de la page redressée ; répétable ; remplace l’estimation automatique), `--output-dpi N`, `--uniform-size`, `--align top-left`,
`--project FILE.lgr` / `--save-project FILE.lgr`. Les TIFF multipages sont lus page par page
(`scan.tif#3` désigne une seule page).

`--skip-blank`, `--skew DEG` (correction fixe), `--rotate 90`, `--pdf-quality N` (0 = sans perte),
`--format png|jpeg|tiff|none`, `--tessdata DIR`, `--psm N`, `--min-conf N`, `--keep-going` (ignorer les
entrées illisibles, code de sortie 2) — voir `legatorocr --help`. On peut donner un dossier au lieu de fichiers. La résolution est
lue dans l’en-tête PNG/JPEG lorsqu’elle indique 150–1200 dpi (sinon 300 ; à forcer avec `--dpi`) ; la rotation
EXIF des appareils photo est appliquée et la transparence est aplatie sur du blanc. Les nombres hors plage sont rejetés
avec un message clair plutôt que de produire des tailles de page absurdes.

## Options moins courantes

`-o, --out-dir DIR` dossier des images de pages traitées · `--no-deskew`, `--max-skew DEG`, `--no-auto-orient`
(pages couchées), `--no-despeckle` (conserver les points parasites) · `--sauvola-k K` (sensibilité du noir et blanc),
`--picture-sensitivity 0-1` (mixed/hybrid) · `--jpeg-quality N` (avec `--format jpeg`) · métadonnées PDF
`--subject`, `--keywords` · `--tesseract PATH` (moteur externe) · `--burst-gap SECONDS` (avec `--burst`),
`--fuse-max-shift PX` (avec `--fuse-frames`) · `--watch-interval SECONDS`, `--watch-skip-existing` (avec
`--watch`) · `--version`. `--project FILE.ScanTailor` ouvre un projet ScanTailor : la liste des scans et la rotation de chaque image sont reprises ; l’inclinaison, le découpage et les zones de contenu sont retrouvés (le lecteur a été écrit à partir de la description du format et testé sur un projet fait à la main, pas sur des fichiers de toutes les versions de ScanTailor).
On peut brancher un autre moteur OCR : `--engine tesseract --tesseract PROGRAM` accepte tout programme qui parle la ligne de commande de Tesseract et renvoie son TSV (modèle et contrat : `docs/examples/external-ocr-engine.py` ; un modèle génératif peut y inventer des mots, gardez donc une personne dans la boucle). Vitesse et précision de l’OCR sur vos propres pages : `scripts/bench-real.py DIR` (images avec un `NAME.txt` de référence chacune ; `--partial` pour des références qui ne couvrent qu’une partie d’une page).
**Pont OCR ONNX** (`scripts/engine-onnx.py` ; Python avec onnxruntime, numpy, Pillow) : exécute une paire PaddleOCR PP-OCR (détecteur de texte DB, puis reconnaisseur CTC) comme ce moteur externe, de sorte qu’un modèle de votre choix puisse servir de moteur OCR sans que LegatorOCR embarque de poids. Vous téléchargez vous-même les modèles, par ex. les modèles de détection et de reconnaissance PP-OCRv6 de la liste de modèles de PaddleOCR convertis en ONNX (`pip install paddle2onnx`, puis `paddle2onnx --model_dir DIR --model_filename inference.pdmodel --params_filename inference.pdiparams --save_file det.onnx --opset_version 14` ; ou un export ONNX prêt à l’emploi depuis un hub de modèles), plus le dictionnaire de caractères correspondant (style `ppocr_keys_v1.txt` : un caractère par ligne ; le pont place le blanc CTC à la classe 0 et ajoute la classe espace, comme PaddleOCR). Utilisation : `export LEGATOROCR_ONNX_DET=det.onnx LEGATOROCR_ONNX_REC=rec.onnx LEGATOROCR_ONNX_DICT=dict.txt` puis `legatorocr scan.png --pdf out.pdf --ocr --engine tesseract --tesseract scripts/engine-onnx.py`. Réglages (variable ou même option, `--onnx-det/-rec/-dict/-size/-rec-height/-thresh/-unclip/-space`) : côté du détecteur 960, hauteur du reconnaisseur 48 (32 pour les anciens modèles), seuil 0,3, unclip 1,5. Les boîtes sont alignées sur les axes, sans texte pivoté ni classifieur d’orientation ; les mots sont séparés à la classe espace d’après le pas de temps CTC (boîtes approximatives) ; la confiance est la probabilité de crête moyenne x 100. **Ce qui est vérifié :** seulement la plomberie, avec de minuscules modèles ONNX synthétiques (`scripts/test-engine-onnx.py` : câblage, coordonnées des boîtes après le redimensionnement, décodage CTC, TSV via la ligne de commande). **Non vérifié :** la précision de reconnaissance avec de vrais modèles PP-OCR (aucun n’a pu être téléchargé là où ceci a été écrit) et si les diacritiques roumains (ă â î ș ț) sortent correctement : cela dépend du modèle et du dictionnaire choisis ; vérifiez sur vos propres pages avec `scripts/bench-real.py` avant de vous y fier. Comme tout moteur à modèle, il peut inventer du texte.
**Famille docTR du pont ONNX (ROADMAP 4.33)** : le même script lit les modèles docTR/OnnxTR, y compris le reconnaisseur à tête roumaine de `tools/ocr-train/romanian_head.py` (ă ș ț Ă Ș Ț ajoutés à un CRNN docTR gelé). `scripts/get-romanian-doctr-models.sh [mobilenet|resnet] [DIR]` télécharge les modèles d’origine depuis les ressources de la publication GitHub d’OnnxTR, construit le reconnaisseur roumain (`romanian_head.py splice`, nécessite python3 avec onnx) et affiche la commande exacte. Utilisation : `export LEGATOROCR_ONNX_FAMILY=doctr LEGATOROCR_ONNX_DET=DIR/db_mobilenet_v3_large-4987e7bd.onnx LEGATOROCR_ONNX_REC=DIR/crnn_mobilenet_v3_small_ro.onnx LEGATOROCR_ONNX_DICT=DIR/vocab_ro.txt` (ou `--onnx-family doctr` etc.), puis `legatorocr scan.png --ocr --engine tesseract --tesseract scripts/engine-onnx.py`. Le détecteur trouve les mots (entrée 1024x1024, seuil de la carte de probabilité 0,3), chaque découpe de mot est lue en 32x128 avec décodage CTC glouton (blanc = dernière classe ; `--onnx-dict` est le vocabulaire sous forme d’une seule chaîne), et le script regroupe lui-même les mots en lignes et en colonnes pour que le TSV soit dans l’ordre de lecture. Mesuré via la vraie ligne de commande sur 12 pages d’un magazine roumain (références ABBYY, non vérifiées à la main ; 2 cœurs CPU) : db_mobilenet_v3_large + crnn_mobilenet_v3_small roumain, CER GOOD8 avec diacritiques 4,26 %, rappel exact des mots 88,2 %, environ 3,4 s par page (l’option `resnet` : 3,67 %, 89,6 %, environ 18 s par page) ; Tesseract `ron` sur les mêmes pages 5,25 %, 91,3 %, 2,7 s par page. Autres polices et scans : non mesurés. Résultat mesuré en une ligne : au niveau de Tesseract pour l’erreur de caractères sur les pages de texte simple (meilleur seulement là où Tesseract lit une illustration comme du texte), en retrait sur le rappel des mots, un seul magazine, références non vérifiées à la main ; voir ROADMAP 4.36.
Les noms d’OCRmyPDF sont acceptés : `-l/--language`, `--force-ocr`, `--redo-ocr`, `--skip-text`, `--deskew` (sans effet, activé par
défaut), `--rotate-pages`, `--output-type pdf|pdfa|pdfa-1|2|3`, `-j/--jobs N`, `--sidecar FILE`, `--image-dpi`
(la sortie se nomme avec `--pdf FILE` ; il n’y a pas de sortie positionnelle). `scripts/check-options.py` liste toute option sans documentation ni test.

## Installation

Téléchargez l’archive de votre plateforme depuis la page des Releases, ou compilez depuis les sources :

```
cargo build --release          # target/release/legatorocr and legatorocr-gui
scripts/package.sh <target>    # e.g. x86_64-unknown-linux-gnu → dist/LegatorOCR-<ver>-<target>.tar.gz
```

| Plateforme | Artefact | Remarques |
|---|---|---|
| Linux x86-64 / ARM64 | `.tar.gz` (+ `.desktop`) | nécessite OpenGL 2+ et X11 ou Wayland |
| Windows x86-64 | `.zip` | nécessite OpenGL 2+ (tout pilote GPU ; les sessions RDP simples peuvent en être dépourvues) |
| macOS Apple-silicon / Intel | `.zip` avec `LegatorOCR.app` | **non signé** : premier lancement par clic droit → Ouvrir, ou `xattr -dr com.apple.quarantine LegatorOCR.app` |

**L’OCR fonctionne d’emblée** avec le moteur natif intégré (`legatorocr-nocr`, Rust pur, sans
installation ; `--engine native`). Il lit les huit langues de l’interface avec un seul modèle plus des
listes de mots par langue. Son modèle a été entraîné sur du texte synthétique, puis affiné sur de vraies lignes numérisées d’un magazine roumain et d’un manuel de 1960 (les scans ne figurent pas dans ce dépôt ; provenance et questions de licence ouvertes : `docs/audit/assets-licences.md`) : sur des pages synthétiques propres et modérément dégradées
il commet moins de 1 % d’erreurs de caractères, mais de vrais scans d’impressions anciennes ou inhabituelles peuvent être moins bons que
Tesseract. `--engine auto` (par défaut) utilise donc **Tesseract lorsqu’il est installé avec les
langues demandées** et se rabat sur le moteur natif sinon ; `--engine tesseract` l’impose.
Tesseract (exécuté comme programme séparé ; l’application le trouve dans le `PATH`) :
`sudo apt install tesseract-ocr tesseract-ocr-ron` · `brew install tesseract tesseract-lang` ·
Windows : `winget install UB-Mannheim.TesseractOCR` (ajoutez-le au `PATH`).
Ces noms de paquets ont été vérifiés le 2026-11-04 (`docs/audit/ocr-externals.md`) : Debian 13 et Ubuntu 24.04 ont `tesseract-ocr` et `tesseract-ocr-ron` ; le `tesseract` de Homebrew est en 5.5.4 avec seulement `eng` et `osd`, et `tesseract-lang` contient les modèles *fast* ; le paquet winget est en retard (5.4.0 de 2024-06). Le fichier `ron` d’`apt`/`brew` est le petit modèle *fast* (environ 2,4 Mo, 2017) ; le modèle *best* (9,6 Mo, même année, même historique de dépôt) se télécharge manuellement : `ron.traineddata` depuis `tesseract-ocr/tessdata_best` vers le dossier tessdata (`--tessdata DIR`). Lequel des deux lit le mieux vos pages n’a pas été mesuré ici.
L’application cherche aussi dans les dossiers d’installation habituels (Homebrew `/opt/homebrew/bin`, `/usr/local/bin`,
`C:\Program Files\Tesseract-OCR`), si bien qu’une application lancée par double-clic fonctionne sans modifier le `PATH`.
Sans Tesseract, le moteur natif est utilisé (l’interrupteur OCR reste actif). Une seule commande pour tous les assistants facultatifs : `legatorocr --install-modules` (affiche les commandes) et `legatorocr --install-modules --yes` (les exécute).
Une compilation **sans le modèle de reconnaissance intégré** (par exemple tant que sa licence n’est pas réglée, `docs/audit/assets-licences.md`) se fait avec `cargo build --release --no-default-features --features lexicon` (ajoutez seulement `--no-default-features` pour omettre aussi les listes de mots) ; toute la suite de tests passe ainsi, `--doctor` signale alors le moteur natif comme absent, et l’OCR nécessite Tesseract ou un moteur externe.
`--auto-rotate` / la case OSD nécessitent en outre `osd.traineddata` (inclus dans les paquets standard).

## Chaîne de traitement

| Étape | Méthode (techniques classiques standard) |
|---|---|
| Orientation | énergie des profils de lignes/colonnes autour de la bande du pas de ligne (0° contre un quart de tour) ; OSD de Tesseract facultatif pour la direction exacte ; ou `--rotate` |
| Découpage de page | gouttière = bande de colonnes la plus vide au centre d’une feuille en paysage (`auto` / `middle` / `off`) |
| Redressement | netteté du profil de projection, recherche grossière→fine jusqu’à 0,01°, rotation bilinéaire ; ou un angle manuel |
| Zone de contenu | blocs d’encre → dilatation → composantes connexes ; poussière et ombres de bord de scanner rejetées, numéros de page conservés |
| Marges / taille | marges en mm, taille de page fixe facultative avec contenu centré ; tout ce qui est hors de la zone de contenu est repeint à la couleur du papier |
| Analyse | tout est mesuré sur une copie d’environ 150 dpi (un scan à 600 dpi est analysé sur 1/16 des pixels) ; le résultat est reporté à la pleine résolution |
| Correction de courbure | les lignes de texte sont suivies à travers de fines bandes verticales (pics du profil de lignes chaînés de bande en bande) ; l’ondulation de chaque ligne autour de sa propre hauteur moyenne devient un champ de rééchantillonnage vertical, interpolé entre les lignes ; ignorée sauf si plusieurs longues lignes montrent une courbure nette |
| Éclairage | `--normalize` : couleur du papier par canal à partir d’une copie d’environ 60 dpi filtrée par maximum puis floutée, puis un gain par pixel |
| Binarisation | Sauvola (par défaut), Wolf, Niblack, NICK, Bradley, Otsu, **auto** (par page : essaie les méthodes locales sur une copie d’environ 150 dpi, garde celle qui a le moins de points isolés et une part d’encre plausible), toutes à partir de sommes de colonnes glissantes en mémoire O(largeur) |
| Nettoyage | `--invert` (négatifs : médiane sombre + queue claire), `--auto-levels` (étirement 0,5 %/99,5 %, un seul gain pour tous les canaux), `--dropout red|green|blue`, `--punch-holes` (taches rondes sombres de 3–10 mm près du bord, remplies de la couleur du papier environnant), `--fingers` (régions couleur peau touchant le bord, jugées par rapport à la couleur du papier), `--remove-lines` (traits ≥ 25 mm et ≤ 1,2 mm d’épaisseur ; les hampes de glyphes qui croisent un filet survivent), `--sharpen` (masque flou ≈0,3 mm), `--despeckle-strength` |
| Images | tuiles à forte part de demi-teintes (le texte est bimodal, les photos sont continues) ou aplats sombres, fermées et filtrées par taille → plages couleur |
| Sortie | couleur, gris, N/B, **mixed** (texte 1 bit + plages couleur) ou **hybrid** (+ couche de fond basse résolution) ; sous-échantillonnage facultatif à `--output-dpi` ; taille de page uniforme fixe ou à l’échelle du livre avec alignement |
| PDF | écrivain propre : JPEG (couleur/gris), CCITT Groupe 4 pour le 1 bit (repli sur Flate quand c’est plus petit), pages en couches (masque pochoir + fond + plages) ; vraie taille de page d’après le DPI |
| Images | PNG avec résolution, TIFF Groupe 4 pour le noir et blanc |
| Problèmes de papier | `--show-through` (égalise l’éclairage, puis ramène au papier les pixels à peine plus sombres que lui ; la vraie encre n’est pas touchée), `--descreen` (les tuiles d’environ 2 mm surtout en demi-teintes et chargées à l’échelle du pixel sont légèrement floutées ; les tuiles de texte sont laissées telles quelles) |
| Feuilles de séparation | `--split-on-barcode` (les pages portant un code-barres, droit, tourné de 180° ou couché, lu sur le scan brut — Code 128, EAN-13, ITF, Code 39 —, démarrent un nouveau document nommé d’après le code → `book_001_ACT-17.pdf`), `--make-separator TEXT` imprime une telle feuille (PNG A4) |
| Navigation PDF | `--bookmarks` (une entrée de plan par fichier source), `--front-matter N` (pages i, ii, iii … puis 1, 2, 3 dans les lecteurs PDF) |
| Zones à effacer | `--erase X,Y,W,H` (mm depuis le coin supérieur gauche de la page, répétable) : peintes à la couleur du papier avant toute mesure ; `erase=` dans les projets `.lgr` ; champ de texte de l’interface |
| Rotation manuelle | dans l’interface, une feuille tournée avec les boutons de rotation (ou ±45°) est verrouillée : l’orientation automatique (vérification intégrée, OSD de Tesseract) n’est pas appliquée par-dessus, même à 0° ; Réinitialiser la rend. Dans les projets : `orient-locked = 1` |
| Zone de travail et ligne de coupe | `--work-area X,Y,W,H` (mm du scan chargé) : tout ce qui est à l’extérieur est peint à la couleur du papier avant toute mesure ; `--cut-at FRACTION` coupe une feuille de deux pages à cette part de sa largeur au lieu de la gouttière ou du milieu (toute rotation ; sur une feuille tournée de 90° ou 270°, les deux pages sortent l’une au-dessus de l’autre). Dans l’interface, les deux se tracent ou se déplacent sur l’original (« Zone de travail », « Ligne de coupe ») ; `work =` et `split-at =` dans les projets `.lgr`. Testé sur des feuilles synthétiques seulement `--cut-angle DEGRÉS` incline la ligne de coupe (±20°, sens horaire) : chaque page garde son côté de la ligne oblique et l'autre côté est peint de la couleur du papier (`cut-angle =` dans les projets). |
| Trapèze et formats de papier | `--keystone-v POURCENT` / `--keystone-h POURCENT` (±30) redressent à la main une feuille photographiée en biais, avant la coupe (`keystone = v, h` dans les projets ; les zones dessinées sur la feuille sont supprimées, les lignes guides suivent) ; `--page-size` accepte aussi `a2`–`a6`, `b3`–`b6`, `letter`, `legal`, `tabloid`. Dans la fenêtre : curseurs dans la barre de page et une liste de formats plus longue ; le bouton **Auto trapez** mesure chaque page après la coupe (inclinaison des lignes, largeur du texte en haut et en bas) et retient une correction pour cette seule page (`pageN.page_keystone = v, h`). Testé sur des feuilles synthétiques ; pas sur de vraies pages courbées |
| Réglages d'une page | Dans un projet, `page1.CLÉ = VALEUR` / `page2.CLÉ = VALEUR` sous `[sheet]` donnent à la page de gauche (ou seule) et à celle de droite d'une feuille coupée leurs propres valeurs de sortie et de nettoyage (`mode`, `despeckle`, `content_adjust`, … ; mêmes clés que les réglages globaux d'un projet enregistré avec `--save-project`). Dans la fenêtre : « Réglages pour : toutes les pages / cette page seulement » au-dessus de Sortie et Nettoyage, et le cadre vert du contenu ne change que la page sur laquelle il est tiré. Essayé sur des feuilles synthétiques et en tests unitaires ; pas à la main dans une fenêtre Un clic sur une page traitée la sélectionne (cadre bleu) ; mode de sortie, nettoyage, trapèze, cadre et crayons OCR n'agissent alors que sur elle ; les zones OCR dessinées sont gardées sous `pageN.page_ocr_zones` / `pageN.page_ocr_ignore`. |
| Zones OCR | `--ocr-zone X,Y,W,H[=LANGUE][#table]` ne lit l'OCR que dans le rectangle (mm sur la page traitée ; `#table` = un seul bloc, ligne par ligne, pour les tableaux), `--ocr-ignore X,Y,W,H` écarte une zone (tampon, en-tête). Dans la fenêtre, trois crayons sur les pages traitées : vert = zone OCR, rouge = ignorer, violet = tableau ; clic droit supprime. Testé avec un moteur simulé ; pas à la main dans une fenêtre |
| Lot | `--skip-duplicates` (pages consécutives dont la différence de vignette 96×128 est ≤ 2/255), `--split-on-blank` (les pages blanches séparent les documents → `name_001.pdf`, …), `--target-size MB` (qualité JPEG choisie d’après un échantillon de pages pour que le PDF tienne dans la taille) |
| Entrée OCR | les pages sous 250 dpi sont agrandies ×2–×4 (Catmull-Rom) avant Tesseract ; les boîtes de mots sont reportées à la taille d’origine |
| Photos de téléphone | `--perspective` : trouve la page comme le grand quadrilatère clair (Otsu + coins extrêmes, avec contrôles de convexité/remplissage) et la redresse par une homographie ; ne fait rien pour les scans droits ou plein cadre |
| Contrôle qualité et archive | `--report r.html` (planche contact, signale les pages blanches / de taille aberrante / fortement redressées), `--multitiff out.tif` (TIFF Groupe 4 multipage, noir et blanc seulement) |
| Livraison | `--checksums` écrit `SHA256SUMS.txt` (même format que `sha256sum`) à côté du PDF pour chaque fichier écrit ; `--verify-sums SHA256SUMS.txt` les revérifie plus tard (code de sortie 1 en cas d’écart ou de fichier manquant) ; `--rights-notice "…"` enregistre une mention de droits (XMP `dc:rights` avec `--pdfa`, sinon la clé d’info `/Rights` et une icône de note sur la page 2) ; `--txt-each` écrit `<nom du pdf>.txt` à côté du PDF pour des indexeurs comme DocFetcher / Agent Ransack ; `--package FOLDER`, `FILE.zip` ou `FILE.iso` (ISO 9660 + Joliet, lisible sous Windows / macOS / Linux ; sans Rock Ridge ni données d’amorçage ; fichiers jusqu’à 4 Gio) rassemble tout ce qui a été écrit plus `SHA256SUMS.txt` et un `MANIFEST.txt` pour la remise (n’écrase jamais ; zip limité à 3 Gio) ; `--package-password-file FILE` (ou `-` avec `LEGATOROCR_PACKAGE_PASSWORD`) chiffre un paquet `.zip` avec WinZip AES-256 ; `--audit-log FILE` ajoute un enregistrement JSON Lines par fichier écrit (heure, version de l’outil, entrées, SHA-256, taille) avec `--retain-until YYYY-MM-DD` et `--legal-hold` facultatifs – il consigne des preuves et ne supprime rien |
| Photos de téléphone | `--phone-paper A4` (ou `A5`, `B5`, `Letter`, `210x297` …) déduit la résolution des photographies qui n’en ont pas à partir du format du papier, en supposant que la prise de vue est cadrée sur la page ; une estimation, faussée de la marge laissée autour de la page |
| Contrôle de cohérence OCR | Avec `--lang ro`, un avertissement quand le texte reconnu contient presque aucun ăâîșț ou beaucoup de mots mêlant lettres et chiffres (typique d’un modèle roumain manquant) ; une note quand `--dpi` est inférieur à 200 ou supérieur à 400 avec `--ocr` |
| Zones d’image | Toujours conservées comme image en couleur dans la sortie mixed / hybrid, pour les photos que le détecteur manque. | Nouvel essai sur pages douteuses (déconseillé) | `--auto-retry` (avec `--ocr` ; `--auto-retry-below FRACTION`) : une page dont la relecture paraît douteuse est retraitée avec d’autres binariseurs / redressement inversé / un autre dpi OCR et l’alternative au meilleur score de type certify est conservée ; `--explain` dit laquelle l’a emporté. **Testé et rejeté :** sur 12 vraies pages il n’a rien changé au seuil par défaut (2803 -> 2803 erreurs de caractères) et +25 erreurs quand on l’impose à chaque page ; sur 8 pages synthétiques dégradées il a fait passer les erreurs de 59 à 424 (une page inclinée est passée de 0 à 354 erreurs). Il est désactivé par défaut et conservé comme simple expérience ; n’en attendez aucun bénéfice (ROADMAP 4.24) |
| Prise en charge | `--ocr-cache DIR` (résultats OCR mémorisés par image de page et réglages ; une nouvelle exécution saute l’OCR des pages inchangées), `--watch DIR` (dossier surveillé : chaque nouveau scan est traité une fois qu’il cesse de grossir ; `--pdf` nécessite `{name}`), `--burst` (photos de téléphone ordonnées par heure de prise de vue EXIF, image la plus nette de chaque rafale conservée ; liste ce qu’il a écarté), `--scan-active` (liste les PDF avec JavaScript, actions de lancement, fichiers incorporés ; un simple coup d’œil statique, un résultat propre n’est pas une garantie) |
| OCR | boîtes de mots du moteur intégré ou de Tesseract → couche de texte invisible (mode de rendu 3, police Type0 sans glyphes + ToUnicode, de sorte que ăâîșț et tout Unicode se copient/recherchent correctement) |

L’export se fait en flux par lots bornés (traiter → OCR → écrire), si bien qu’un livre en couleur de plusieurs centaines de pages
n’a pas besoin de tenir en mémoire.

Crates : `legatorocr-core` (chaîne de traitement) · `-pdf` (écrivain) · `-ocr` (choix du moteur, pilote Tesseract, sorties hOCR / JSON) · `-nocr` (moteur OCR intégré) ·
`-engine` (orchestration d’export partagée) · `-cli` · `-gui` (egui/eframe).

Contrôles qualité : voir `FUZZING.md` (10 suites de fuzzing/propriétés, exécutées chaque semaine en CI avec recoupements qpdf/poppler).

## Export de passages

`--passages-jsonl FILE` (avec `--ocr`) écrit du JSON Lines : UTF-8, un objet par ligne, une ligne par
paragraphe de chaque page conservée, pages dans l’ordre de sortie, paragraphes dans l’ordre de lecture du moteur (sur
une page à deux colonnes, les boîtes des deux colonnes sont donc listées colonne par colonne et peuvent se
chevaucher). Les paragraphes sont ceux qu’utilise `--docx` (`words_to_paragraphs`), pas une seconde
détection. Chaque clé est toujours présente ; une valeur inconnue vaut `null`.

| Clé | Type | Signification |
|---|---|---|
| `schema` | chaîne | toujours `"legatorocr.passage/1"` |
| `passage_id` | chaîne, 16 hexadécimaux minuscules | 16 premiers chiffres du SHA-256 de `"<page_image_sha256>:x0,y0,x1,y1"` (les nombres de `bbox_px`) ; la même image de page et la même boîte donnent toujours le même identifiant, unique dans le fichier |
| `source_file` | chaîne | nom de fichier de l’entrée (avec `#N` pour la page N d’une entrée multipage) |
| `page` | entier >= 1 | numéro de page dans la sortie (après suppression des pages blanches et des doublons ; une double page découpée compte pour deux) |
| `page_label` | chaîne ou `null` | numéro de page imprimé, seulement avec `--page-labels` et seulement là où sa règle de suite étiquetterait la page PDF ; sinon `null` |
| `paragraph_index` | entier >= 0 | 0, 1, 2, ... dans la page |
| `text` | chaîne, non vide | le paragraphe ; lignes séparées par `\n`, mots par une espace. Avec `--clean-text`, le nettoyage est appliqué au paragraphe, donc le texte est celui que montre `--txt` |
| `bbox_px` | 4 entiers | `[x0, y0, x1, y1]` en pixels de l’image de la page de sortie, origine en haut à gauche, `x1`/`y1` exclus ; `0 <= x0 < x1 <= page_width_px`, de même pour y |
| `bbox_frac` | 4 nombres | la même boîte divisée par la largeur / hauteur de page, 6 décimales, entre 0 et 1 |
| `page_width_px`, `page_height_px` | entiers | taille de l’image de la page de sortie |
| `language` | chaîne | le réglage de langue OCR utilisé pour la page (codes Tesseract tels que `ron+eng`, en respectant `--page-lang`) ; c’est le réglage, pas une langue détectée |
| `mean_confidence` | nombre 0..100 ou `null` | moyenne des confiances de mots du moteur dans le paragraphe, 2 décimales ; `null` si aucun mot n’en a |
| `page_image_sha256` | chaîne, 64 hexadécimaux minuscules | SHA-256 des octets de l’image de la page (voir `page_image_basis`) |
| `page_image_file` | chaîne ou `null` | nom de cette image dans `-o` quand elle a été écrite (`--format png/jpeg/tiff`) ; sinon `null` |
| `page_image_basis` | `"file"` ou `"png-encoding"` | `"file"` : l’empreinte porte sur le fichier image écrit. `"png-encoding"` (avec `--format none`) : aucune image n’a été écrite ; l’empreinte porte sur les octets PNG que `--format png` écrirait pour cette page |
| `cite` | chaîne | `"<title> p.<label>"` : le titre est `--passages-title` ou le nom du fichier source sans extension ; l’étiquette est `page_label`, sinon `page` |

Vérifier un fichier (Python de la bibliothèque standard seulement) : `python3 scripts/check-passages.py out.jsonl [--txt out.txt] [--images DIR]`.
Il contrôle chaque clé et chaque type, que chaque boîte se trouve dans sa page, les fractions, l’empreinte de l’identifiant, la
forme de `cite` et, avec `--images`, les empreintes d’images par rapport aux fichiers écrits ; avec `--txt`, il
compare les passages de chaque page avec la même page de la sortie `--txt` (espaces
réduits) et affiche le pourcentage de concordance. Le format est propre à LegatorOCR ; la capacité d’un outil de
recherche donné (par exemple TEZAUR) à l’importer n’a pas été vérifiée.

## Assistant de capture par téléphone

`web/capture/index.html` est un seul fichier HTML hors ligne (aucune requête externe, aucun stockage, aucune télémétrie ; anglais et roumain, textes dans un seul objet). Ouvrez-le sur un téléphone (une caméra exige https ou localhost sur la plupart des navigateurs ; `file://` fonctionne dans certains), démarrez la caméra, posez la page sur une surface plus sombre. Il trouve la page claire (seuil d’Otsu, plus grande région connexe, coins par x+y / x-y extrêmes, donc jusqu’à environ 45 degrés de rotation), trace le contour, et déclenche tout seul quand le contour est resté immobile pendant 0,8 s et que la page passe les contrôles ; sinon il dit pourquoi : aucune page trouvée, page pas entièrement visible, trop flou (variance du laplacien), trop sombre, trop clair. Un bouton manuel, une bande de vignettes avec suppression, et « Enregistrer la rafale en ZIP » (ZIP sans compression écrit à la main) donnent `burst-YYYYMMDD-HHMMSS.zip` avec `page-0001.jpg`, `page-0002.jpg`, ... à la résolution du flux de la caméra (une image vidéo, pas forcément la pleine résolution photo du capteur). Chaque JPEG porte une heure de prise de vue EXIF, au moins 4 s après la précédente, afin que `legatorocr --burst` (par défaut `--burst-gap 3`) conserve l’ordre et ne prenne pas deux pages pour une seule rafale. Ensuite : `legatorocr --burst --pdf book.pdf page-*.jpg`.
Testé seulement sur des images **synthétiques** dans Chromium sans écran avec une fausse caméra (`scripts/test-capture-assistant.py`) : erreur de coin de 1,0-2,1 px à 640 de large sur 6 placements (rotation de -14 à +31 degrés, décalages, une distorsion trapézoïdale), les refus se déclenchent avec la bonne raison, le ZIP passe `zipfile.testzip` et `unzip -t`, et `--burst` accepte les pages décompressées. **Non testé :** vrais téléphones, vrais éclairages et ombres, flou de bougé, mise au point automatique, Safari iOS, un bureau clair ou blanc (la page se confond alors avec le fond), le refus « trop clair ». Tous les seuils sont des estimations non calibrées.

## Indices d’intégrité (`--integrity-hints`)

**Risque ÉLEVÉ de fausses alertes. Lisez ceci avant de l’utiliser.** `--integrity-hints FILE.json` (sur option, s’exécute sur les images d’entrée telles quelles, avant tout nettoyage) écrit, par page, des boîtes en pixels de page qu’une personne voudra peut-être revoir, chacune avec une explication en langage clair de « ce que cela signifie » et des « causes anodines courantes ». C’est une liste de choses *à vérifier*, jamais un verdict ; la sortie ne dit pas qu’un document est authentique ou non. Ne l’utilisez pas comme seule base d’une décision concernant une personne ou le diplôme d’une personne ; interrogez l’établissement émetteur.

Signaux (`--integrity-signals LIST` ; `all`, `default`, ou des noms) :
| Signal | Ce qui est examiné | Actif par défaut |
|---|---|---|
| `copy_move` | blocs 16x16 identiques (hachés ; papier blanc et glyphes répétés plus de quelques fois ignorés) à deux endroits, à n’importe quel décalage de pixels ; boîtes d’au moins 64 px des deux côtés | **oui** |
| `jpeg_grid` | entrées JPEG : une fenêtre de 128 px dont le motif de bords de blocs 8x8 est décalé par rapport au reste de la page | non : 4 pages non modifiées sur 12 signalées, 0 modification sur 60 trouvée |
| `jpeg_double` | entrées JPEG : motif en peigne d’un second enregistrement (la statistique de `--verify-document`, page entière) | non : aucune fausse alerte, mais 0 page modifiée sur 60 signalée dans le test ci-dessous |
| `noise` | tuiles dont le bruit fin vaut 3 fois la médiane de la page | non : 10 pages non modifiées sur 12 signalées |
| `line_size` | nécessite `--ocr` : un mot dont la hauteur ou la position est en décalage avec sa ligne de texte | non : 12 pages non modifiées sur 12 signalées |

Mesuré sur des modifications **synthétiques** seulement (12 vraies pages du jeu de test OCR, JPEG q85 ; modifications : une suite de chiffres dessinée sur un mot, une pièce de 220x140 copiée ailleurs, une pièce de 260x180 issue d’une copie q45 collée à un décalage impair, du bruit gaussien en 240x160 ; chaque page modifiée réenregistrée en q85 ; et les pages intactes enregistrées une fois, réenregistrées une fois en q85, réenregistrées encore en q75 ; `docs/experiments/integrity_eval.py`, ROADMAP 7.5c). `copy_move` : a trouvé 10 pièces copiées sur 12, 0 page non modifiée/réenregistrée sur 36 signalée ; il ne trouve **pas** un chiffre ou un mot retapé, et il manque les pièces de moins de 64 px. La limite de taille a été fixée après avoir vu des fausses alertes sur les mêmes pages, ce chiffre est donc optimiste. Ces nombres ne disent rien des vrais faux, qui sont faits avec d’autres outils, d’autres polices et une autre compression ; les vrais tampons, logos répétés et en-têtes de lettre n’étaient pas dans le test et sont la source attendue de fausses alertes. Les autres signaux sont disponibles avec `--integrity-signals all` pour la recherche seulement.

## Limites connues

Voir `COMPARISON.md` pour ce que font d’autres outils et que celui-ci ne fait pas. En bref :

- **Orientation** : le test intégré trouve seulement « la page est couchée », pas *dans quel sens*. **L’orientation par OCR**
  (interrupteur de l’interface / `--auto-rotate`) tranche entre 90° et 270° et les pages à l’envers : avec les données `osd` de Tesseract quand elles sont
  installées, sinon avec le moteur intégré, qui lit une copie réduite dans les quatre rotations et garde celle dont les
  mots se trouvent dans les listes de mots de la langue (il faut environ une douzaine de lettres de texte imprimé ; sinon la page est laissée
  telle quelle). Solution manuelle : *Pivoter à gauche/à droite de 90°* / `--rotate`.
- Zones à effacer : saisies en millimètres (identiques sur chaque page) ou tracées à la souris par feuille (glisser sur la vue Original, clic droit pour supprimer ; enregistrées dans le projet) ; les zones d’image se tracent de la même façon (bleu) ; les lignes-guides de correction de courbure aussi (à main levée, type *Ligne-guide* ; aussi saisies via `--dewarp-guide` / le champ de l’interface). Le tracé dans l’interface n’a pas été testé visuellement.
  Les images sont aussi détectées automatiquement
  (sensibilité réglable) et la zone de contenu peut être ajustée page par page (champs numériques ou en faisant glisser ses bords verts dans l’interface ; sur une double page découpée, l’ajustement s’applique aux deux pages).
- La correction de courbure ne corrige que la courbure verticale des lignes de texte (ni perspective ni étirement horizontal).
- `--pdfa` écrit la *structure* PDF/A-2b (police de texte TrueType incorporée sans glyphes, paquet XMP concordant avec le dictionnaire Info, profil sRGB d’intention de sortie incorporé, gris CIE, ID de fin de fichier). La police, le profil ICC et le XMP ont été vérifiés avec fontTools, LittleCMS et un analyseur XML, et le fichier avec qpdf et poppler, et la tâche CI `PDF/A validation` exécute veraPDF (greenfield 1.30.x, profil PDF/A-2b) sur des fichiers d’exemple générés — noir et blanc, mixed, hybrid, gris, avec et sans couche OCR, une et deux pages — et échoue si l’un est rejeté. C’est un test de ces échantillons, **pas une certification** de toutes les sorties possibles. Entrée PDF : décodage Huffman JBIG2 vérifié par rapport à pdfium sur des flux générés (la variante à bitmap collectif MMR seulement par rapport à notre propre décodeur G4, pdfium la rend vide) ; raffinement/agrégation Huffman (raffinement de région de texte, symboles raffinés et d’agrégat ; tables personnalisées) vérifiés par rapport à poppler et, sauf pour les décalages de raffinement RDW/RDH au-delà de -2..1, pdfium (pdfium centre la référence avec RDW>>2 au lieu de RDW>>1 dans les régions de texte Huffman, et décode mal le cas de même taille à décalage nul ; poppler et notre décodeur suivent la norme), les symboles raffinés vides dans les dictionnaires d’agrégat Huffman étant refusés ; les styles de bloc de code JPEG 2000 dont bypass/termall, POC, PPM et PPT ont été vérifiés par rapport à OpenJPEG 2.5 sur environ 1 350 flux générés (sans perte exact, 9/7 à 2 niveaux de gris près ; les flux PPM/PPT ont été produits en réécrivant ceux d’OpenJPEG, qu’OpenJPEG a ensuite décodés à l’identique), palettes JPEG 2000 et style de bloc de code à haut débit (Partie 15) non pris en charge, prédiction typique JBIG2 pour les régions de raffinement (TPGRON) et grilles de demi-teintes décalées vérifiées seulement par rapport à notre propre encodeur (poppler les décode différemment) ; fichiers chiffrés : les mots de passe utilisateur et propriétaire ont été vérifiés sur des fichiers faits avec qpdf (RC4-40/128, AES-128, AES-256 R5/R6) ; codes-barres : Code 128 (jeux A/B/C), EAN-13, ITF, Code 39 sont lus, seul le Code 128 est imprimé. JBIG2 et Groupe 3 ont été vérifiés par rapport à la sortie de poppler / libtiff ; la composition des pages en couches seulement par rapport aux pages de notre propre écrivain.
- La correction de perspective nécessite une page nettement plus claire que son environnement et montrant ses quatre coins ; sinon elle laisse la photo telle quelle. Elle ne déroule pas les pages courbes (utilisez `--dewarp`).
- Le retrait de la peau/des trous/des doigts relève de l’heuristique : `--fingers` est désactivé par défaut et peut manger des photographies de teinte chair au bord de la page.
- Le DPI est lu dans les en-têtes PNG/JPEG (150–1200 dpi ; 50–149 seulement quand la taille de page qui en découle est plausible, et jamais 72/96, que les éditeurs écrivent par défaut) mais pas dans les en-têtes TIFF : réglez `--dpi` à la main en cas de doute ; un TIFF 16 bits est ramené à 8 bits.
- Inclinaison : les pages presque sans encre sont laissées telles quelles, et quand les lignes de texte et la structure verticale donnent chacune un angle net mais différent (dessins obliques, hachures), la page n’est pas pivotée. Les pages déjà simples et droites doivent être traitées avec `--split off`.
- Une bordure sombre de la vitre du scanner *touchant* le texte peut encore agrandir la zone de contenu détectée
  (les bordures et ombres de coin séparées du texte sont retirées).
- Les compilations Windows et macOS proviennent des workflows CI (`.github/workflows`) ; l’environnement de
  développement de l’auteur n’a vérifié que Linux.
- Publications : **Actions → Release → Run workflow** (saisissez une étiquette comme `v0.2.0-pre.1`), ou poussez une étiquette
  `v*`. Le workflow exécute d’abord toute la matrice CI, puis compile les cinq plateformes et ouvre une pré-publication
  **brouillon** à relire ; rien n’est publié tant que vous n’appuyez pas sur Publish.
